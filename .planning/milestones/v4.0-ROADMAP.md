### Phase 1: Query Generation
**Goal**: The packaging material search query planning system uses LLM-driven reasoning to generate industry-appropriate visual search keywords in English from Chinese IP profiles and script content
**Depends on**: Nothing (milestone start)
**Requirements**: QGEN-01, QGEN-02, QGEN-03, QGEN-04
**Success Criteria** (what must be TRUE):
  1. When an AC repair IP profile and script are submitted, the system generates English search queries like "HVAC technician", "air conditioner maintenance", "commercial cooling unit" — never generic builders or lakes
  2. When a restaurant IP profile and script are submitted, queries distinguish between product_detail role ("fried rice close-up", "wok cooking"), store_environment ("restaurant interior"), and process ("chef cooking in kitchen")
  3. The system refuses to generate queries for credentials, fake_case, and emotional_appeal roles — returns empty for those roles
  4. If the LLM fails or returns unusable keywords, the system falls back to deterministic mapping using 20-industry Chinese-to-English archetype table (空调维修 → air conditioning repair)
**Plans:** 2 plans
Plans:
- [x] 01-01-PLAN.md — LLM query planning with industry-specific prompt, role semantics, and few-shot examples
- [x] 01-02-PLAN.md — Deterministic fallback with 20-industry Chinese-to-English visual archetype mapping

### Phase 2: Infrastructure Prerequisites
**Goal**: Stock media suggestions return immediately with pending status while OSS transfers happen asynchronously in the background, and cache schema versioning enables scoring-safe cache invalidation when relevance logic changes
**Depends on**: Phase 1
**Requirements**: INFRA-01, INFRA-02
**Success Criteria** (what must be TRUE):
  1. When packaging material suggestions are generated, the API returns URLs immediately with transferStatus=pending, and OSS transfer happens in background
  2. When cache logic or scoring algorithm changes, incrementing CACHE_VERSION invalidates all old entries — no stale pre-scored results leak into new scoring rules
  3. The system logs transfer failures with enough context to debug (source URL, error, retry attempt)
**Plans:** 2 plans
Plans:
- [x] 02-01-PLAN.md — Async OSS transfer with pending/completed/failed status
- [x] 02-02-PLAN.md — Cache schema versioning for scoring-safe cache invalidation

### Phase 3: Relevance Scoring and Fallback
**Goal**: Stock media suggestions are filtered by two-tier relevance scoring (deterministic pre-filter + LLM batch), abstract concept keywords provide tone-appropriate fallback for low-scoring results, and below-threshold results are filtered before display
**Depends on**: Phase 2
**Requirements**: SCORE-01, SCORE-02, SCORE-03, SCORE-04
**Success Criteria** (what must be TRUE):
  1. When search results have file names or alt text matching query keywords (case-insensitive, partial match), they bypass LLM scoring and score 0.9
  2. When search results don't match deterministic filter, they are sent to LLM in batches of 10 with query context, receiving scores 0.0-1.0
  3. When fewer than 3 results score above 0.6 threshold, system appends abstract resource fallback using industry + tone keywords (e.g., "professional business" for AC repair)
  4. Results below 0.6 threshold are filtered before reaching the frontend — users only see relevant suggestions
**Plans:** 2 plans
Plans:
- [x] 03-01-PLAN.md — Two-tier relevance scoring (deterministic pre-filter + LLM batch scoring)
- [x] 03-02-PLAN.md — Abstract resource fallback with tone-appropriate visuals

### Phase 7: API Integration & DB Foundation
**Goal**: The system can submit video enhancement jobs to Aliyun EnhanceVideoQuality API, poll for completion status, transfer temporary result URLs to OSS before 30-minute expiry, and persist enhancement state in the database with zero-downtime schema migration
**Depends on**: Phase 6 (v2.0 complete)
**Requirements**: ALIYUN-01, ALIYUN-02, ALIYUN-03, ALIYUN-04, INFRA-01
**Success Criteria** (what must be TRUE):
  1. The system submits a 1080p video URL to Aliyun EnhanceVideoQuality API with target resolution 3840x2160 and receives a RequestId and JobId in response
  2. The system polls GetAsyncJobResult every 30 seconds until job status reaches PROCESS_SUCCESS or PROCESS_FAIL
  3. When enhancement completes, the system downloads the video from the temporary Aliyun URL and transfers it to OSS at `videos/{taskId}/enhanced-4k.mp4` before the 30-minute expiry window
  4. The VideoTask table has nullable enhancement fields (enhancementStatus, enhancementJobId, enhanced4kUrl, enhancementStartedAt, enhancementCompletedAt, enhancementError) accessible via Prisma with zero downtime during migration
  5. Aliyun credentials are configured via environment variables and RAM user has AliyunVIAPIFullAccess permission verified via CLI test call
**Plans:** 2 plans
Plans:
- [x] 07-01-PLAN.md — Install Aliyun SDK, add enhancement fields to VideoTask schema, update API types
- [x] 07-02-PLAN.md — Aliyun VIAPI API client and enhancement lifecycle module with OSS transfer

### Phase 8: Enhancement Pipeline
**Goal**: Enhancement is automatically triggered after video completes 1080p delivery, runs asynchronously with independent lifecycle tracking, is detected via webhook with polling backup, and preserves 1080p access on any failure
**Depends on**: Phase 7
**Requirements**: ENHANCE-01, ENHANCE-02, ENHANCE-03, ENHANCE-04, INFRA-02
**Success Criteria** (what must be TRUE):
  1. When a video task reaches status=completed and deliveryStatus=durable, the system automatically triggers enhancement without blocking 1080p delivery to the user
  2. The enhancementStatus field cycles independently from video status: none → pending → processing → completed or failed, and never prevents videoUrl access
  3. Enhancement completion is detected first via Aliyun webhook callback with Redis deduplication, backed by a cron job polling every 2 minutes for in-progress enhancements
  4. When enhancement fails (API error, timeout, transfer failure), the system marks enhancementStatus=failed, logs the error, and leaves videoUrl pointing to the working 1080p file
  5. Kubernetes cron job is deployed to poll in-progress enhancements every 2 minutes, with zombie expiry marking jobs as failed if processing exceeds 2 hours
**Plans:** 2 plans
Plans:
- [x] 08-01-PLAN.md — Enhancement trigger in settleVideoTaskSuccess and Aliyun webhook handler with Redis dedup
- [x] 08-02-PLAN.md — Enhancement polling with zombie expiry, cron endpoint, and K8s CronJob

### Phase 10: Data Infrastructure & AI Generation Engine
**Goal**: The database schema supports dual-version IP profiles (v1 flat + v2 3D positioning), AI generation API produces structured three-dimensional positioning from 5-question input with Zod validation and auto-fix retry logic, and all existing users continue working on v1 without interruption
**Depends on**: Phase 9 (v3.0 complete)
**Requirements**: DATA-01, DATA-02, DATA-03, DATA-04, DATA-05, DATA-06, AIGEN-01, AIGEN-02, AIGEN-03, AIGEN-04, AIGEN-05, AIGEN-06
**Success Criteria** (what must be TRUE):
  1. The IpProfile table has profileVersion field (default 1), 5 survey input fields (surveyIndustry, surveyTargetCustomer, surveyMonetization JSON, surveyPersonalTraits, surveyContentGoal), and 3D positioning fields (business/persona/content as JSON) — deployed via migration with zero downtime
  2. GET /api/ip-profile returns both v1 flat fields and v2 3D positioning fields when present; PUT accepts either v1 or v2 field structures and persists correctly
  3. buildIpProfilePromptSnapshot generates different context snapshots based on profileVersion: v1 uses 7 flat fields, v2 uses 3D positioning structure
  4. isComplete and getMissingFields logic returns correct completion status for v1 (7 flat fields) vs v2 (3D positioning sections presence)
  5. POST /api/ip-profile/generate-positioning accepts 5-question JSON input, calls LLM with structured prompt enforcing three-dimensional methodology, validates response with Zod schema (exact field counts, ratio sum = 100), and returns structured 3D positioning JSON
  6. When Zod validation fails, the system applies auto-fix (normalize ratios, retry with lower temperature) up to 2 retries before returning error
  7. LLM prompt includes prompt injection protection (input sanitization, XML delimiters, role anchoring) and quality gate instructions rejecting generic/boilerplate responses
**Plans**: 2 plans
Plans:
- [x] 10-01-PLAN.md — Database schema migration with dual-version fields and version-gated utilities
- [x] 10-02-PLAN.md — AI generation endpoint with Zod validation, auto-fix, and retry logic

### Phase 11: Frontend Wizard & 3D Result Display
**Goal**: New users complete a 5-question stepper wizard with card-based selection and text input, AI generates 3D positioning with loading animation, results display as three cards (Business/Persona/Content) with inline editing and badge management, and the flow is fully mobile-responsive with immersive one-question-per-screen UX
**Depends on**: Phase 10
**Requirements**: UI-01, UI-02, UI-03, UI-04, UI-05, UI-06, UI-07
**Success Criteria** (what must be TRUE):
  1. When a new user (profileVersion=null or 1 with incomplete fields) visits IP profile page, they see a 5-question stepper wizard with progress indicator showing "1/5", "2/5", etc.
  2. Question 1 (industry), 3 (monetization), and 5 (content goal) display card-based single-selection UI; questions 2 (target customer) and 4 (personal traits) display text area input
  3. After completing all 5 questions and clicking "Generate", the system displays a loading screen with progressive status messages ("Analyzing your answers...", "Building positioning...", "Finalizing...") for 3-8 seconds
  4. When generation completes, user sees three cards labeled "Business Positioning", "Persona Design", "Content Strategy", with a one-line AI summary at the top ("Your IP positioning: [summary]")
  5. Each sub-field within the three cards is click-to-edit (inline text editing for strings, badge add/remove for tag arrays), and changes save on blur
  6. User sees "Confirm & Save" and "Re-generate" buttons at the bottom; clicking Confirm persists profileVersion=2 and all 3D positioning data
  7. Returning users (profileVersion=2 with complete 3D positioning) see a dashboard view with the three cards in read mode and "Edit" buttons, not the wizard
  8. On mobile (375px-768px), the stepper displays full-screen immersive layout with bottom sticky CTA, one question per screen, swipe-friendly card selection
**Plans**: 2 plans
Plans:
- [x] 11-01-PLAN.md — API client function, view state machine, 5-question stepper wizard, generation loading screen
- [x] 11-02-PLAN.md — Three-card result display with inline editing, badge management, dashboard view, visual verification

# Roadmap: ClipFlow — v1.0 Smart Material Matching

## Overview

The packaging pipeline already retrieves stock media but accepts whatever the APIs return first -- no relevance gate exists. This produces the documented failure: an HVAC repair business gets birds, lakes, and construction workers instead of HVAC-specific content. This milestone attacks the problem at two layers: upstream (better query generation grounded in industry-specific visual vocabulary) and downstream (post-search relevance scoring that rejects off-domain results). Three phases execute in strict dependency order: fix queries at the source (highest leverage, zero infra cost), prepare infrastructure for the scoring layer (OSS decoupling + cache versioning), then add two-tier relevance scoring with abstract fallback as the final quality gate.

## Phase Details

### Phase 1: Query Generation
**Goal**: Stock media queries accurately reflect the user's specific business and industry instead of producing vague generic keywords
**Depends on**: Nothing (first phase)
**Requirements**: QGEN-01, QGEN-02, QGEN-03, QGEN-04
**Success Criteria** (what must be TRUE):
  1. An HVAC repair business receives search queries containing HVAC-specific visual terms (e.g., "HVAC technician outdoor unit", "air conditioning repair tools") instead of vague terms like "small business process" or "repair work"
  2. Each material role (product_detail, store_environment, process) produces visually distinct query types -- product_detail queries target object close-ups, store_environment queries target business spaces, process queries target work being performed
  3. The deterministic fallback path (`getFallbackQuery`) produces business-specific keywords derived from the IP profile's industry and primaryOffer fields, not a generic "small business" catch-all
  4. Testing against 5 industry archetypes (HVAC, bakery, aesthetic clinic, custom furniture, postpartum care) confirms that primary queries return totalResults >= 10 from Pexels for at least 4 out of 5 industries

### Phase 2: Infrastructure Prerequisites
**Goal**: The suggestion endpoint returns fast with pending OSS status and the cache layer is ready for scoring deployment
**Depends on**: Phase 1
**Requirements**: INFRA-01, INFRA-02
**Success Criteria** (what must be TRUE):

  2. PexelsQueryCache includes a schemaVersion field, and cache lookups filter by the current schema version so that pre-scoring cached results are treated as cache misses after scoring is deployed
  3. The production-plan submission endpoint still rejects materials with `ossStatus !== "ready"` -- the durability gate at submission time is preserved even though the suggestion endpoint no longer blocks on transfer

### Phase 3: Relevance Scoring and Fallback
**Goal**: Irrelevant stock media results are rejected before being presented as suggestions, and when insufficient relevant results exist, the system provides contextually appropriate abstract visuals instead of accepting off-domain images
**Depends on**: Phase 2
**Requirements**: RSCO-01, RSCO-02, RSCO-03, FBACK-01, FBACK-02
**Success Criteria** (what must be TRUE):
  1. A stock media result with alt text like "mountain lake reflection" is rejected for an HVAC business -- the deterministic pre-filter catches obviously irrelevant results without any LLM cost
  2. When deterministic filtering yields fewer candidates than needed, LLM batch scoring evaluates remaining candidates in a single call per query-entry and rejects results below the relevance threshold
  3. Results below the relevance threshold are filtered out before being presented as suggestions, regardless of their API ranking position
  4. When scoring produces fewer results than the role's count requires, the system fills remaining slots with abstract/generic visuals (patterns, textures, business-themed graphics) rather than accepting irrelevant concrete images
  5. Abstract fallback visuals are contextually appropriate to the business tone -- professional services receive clean/minimal abstracts, food businesses receive warm/textured abstracts -- and are distinguishable in the API response so the frontend can display them in a distinct visual state
**Plans:** 2/2 plans complete

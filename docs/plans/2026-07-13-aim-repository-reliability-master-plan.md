## 0. 先读结论

这不是一次“大重构”，而是一组按风险排序、可独立验证、可逐批合并的治理任务。最终目标不是让目录看起来更整齐，而是同时做到：

1. 每次发布都能证明代码、Schema、迁移、测试和线上依赖一致。
2. AIM 的路由、上下文、模型降级和错误恢复可解释、可追踪、可复现。
3. 用户输入、项目资料、知识库和生成内容不会越权、泄露或被错误当成事实。
4. 新功能继续按 `aim/`、`topics/`、`competitor/` 等领域演化，页面和 API Route 只做拼装与协议适配。
5. 单个智能体只能执行一个任务包，不允许顺手跨领域重构。

最高风险不再是某个文件超过 800 行。当前更值得担心的是：测试门禁不可信、接口契约缺失、迁移有两个真源、令牌保存在浏览器本地、错误被静默降级、外部调用缺少统一韧性，以及用户失败后不知道系统做到哪一步。

以下事实来自 2026-07-13 对当前工作树的静态检查和已执行验证，执行智能体必须先复核，不得直接当成永恒事实：

| 项目 | 当前事实 | 风险 |
|---|---|---|
| Prisma | 原 1324 行 Schema 已拆为 9 个领域文件，主文件 8 行；改动尚未提交 | 其他 AI 若从旧提交开工，会重新制造冲突 |
| Schema 验证 | `prisma validate`、`generate`、`migrate diff` 已通过，diff 为无差异 | 尚未经过合并后的 CI 与生产迁移状态验证 |
| 文件体积 | 非生成 TS/TSX/MJS 最大约 500 行；Prisma 单文件上限 400 | 现有防线有效，不能把阈值再调高 |
| 单元测试 | 695/713 通过，仍有 18 个既有失败 | 任何“测试通过”结论目前都不可信 |
| E2E | 全量执行出现数据库初始化超时/挂起，已人工停止 | 发布门禁不能依赖这套 E2E |
| API | `apps/web/src/app/api` 约 168 个 route 文件 | 权限、输入、错误格式和版本兼容面过大 |
| 输入校验 | 约 83 个 API Route 直接调用 `request.json()`；API Route 内未发现 Zod 使用 | 非法输入可能进入 Service 或 Prisma 才失败 |
| 限流 | API 与 lib 中仅少量限流引用 | 登录、生成、抓取、导入和外部 Agent API 有滥用风险 |
| 数据迁移 | `api/admin/migrate` 仍可执行裸 `ALTER TABLE` | Prisma Migration 与管理员接口形成双真源 |
| 环境变量 | `prisma.config.ts` 在缺少 `DATABASE_URL` 时回退到默认本地连接串 | 配错环境时不会立即失败，可能操作错误数据库 |
| 鉴权 | 用户和管理员 Bearer Token 持久化在 `localStorage` | XSS 可直接窃取长效 Token，管理员风险更高 |
| Web 安全头 | 未发现统一 CSP、HSTS、X-Content-Type-Options 等应用层配置 | 需结合 Nginx 实际配置复核，当前不能证明已覆盖 |
| 错误处理 | 源码存在大量 `console.*` 和空 catch/空数组降级 | 真实故障容易被伪装成“没有数据”或“网络超时” |
| 健康检查 | `/api/healthz` 只检查数据库和 Redis | LLM、OSS、关键外部服务与 Worker 不在发布证据中 |
| LLM | 有模型路由、超时、fallback 和 token 记录，但缺少统一成本预算 | fallback 可能放大延迟、成本和输出差异 |
| 数据留存 | AIM Harness 保存完整 Prompt/消息快照 30 天 | 需要字段脱敏、最小化、访问审计和删除政策 |
| 数字人 | 页面已开始删除，但仍有 avatar、voice、auth-video、public-preview 等路由/模型引用 | 半删除状态会继续增加维护面和错误入口 |
| 仓库治理 | 有部署、架构与 Eval Workflow；未发现 CODEOWNERS、依赖扫描、密钥扫描、SBOM | 责任边界和供应链风险缺少自动防线 |

## 2. 全局成功标准

全部任务完成不等于“所有代码都重写”。只有满足以下条件才算完成：

- `main` 上不存在未解释的失败测试；隔离环境中的全量单测、关键集成测试、E2E 都可重复通过。
- 发布顺序固定为：代码质量 -> 测试 -> 构建 -> 迁移预检 -> 迁移 -> 部署 -> 健康检查 -> 冒烟测试；失败能自动阻断或回滚。
- 数据库结构只有 Prisma Schema + Migration 一个真源，生产环境不存在临时裸 SQL 接口。
- 所有写接口、昂贵接口和外部 Agent API 都有运行时输入校验、权限校验、限流和统一错误码。
- 所有项目级资源都经过统一的 `userId + projectId + resourceId` 授权校验，禁止只凭前端传入 ID 查询。
- 用户/管理员认证不再依赖可被任意脚本读取的长期 `localStorage` Token。
- AIM 每次执行都能回答：命中了什么动作、用了哪些来源、选了哪个模型、是否降级、失败在哪一步、是否可继续。
- 用户在生成、选题、竞品刷新、知识导入失败后，可以重试或恢复，不需要重新输入全部资料。
- 关键链路日志结构化并带统一 `requestId/runId/userIdHash/projectId`；日志默认不记录原始 Prompt、Token、密码和完整个人资料。
- 领域代码进入 `src/features/<domain>`，页面和 API Route 不新增业务算法；当前 500 行源码上限和 400 行 Prisma 上限继续生效。
- 数字人能力按用户决定完整删除，不保留“以后可能用”的半套入口；删除前只做依赖和生产数据清点。

## 3. 明确不做

- 不一次性重写 Next.js、Prisma、鉴权或 AIM Harness。
- 不为了目录漂亮移动所有历史代码。
- 不新增微服务；先维持可治理的模块化单体。
- 不把 500 行上限放宽到 800 行。
- 不把页面组件、Service、Repository 全部套入统一基类。
- 不为单次使用创建通用框架。
- 不把模型生成内容写成已确认事实。
- 不恢复此前已拒绝的“视频生成三层边界”规则。
- 不保留数字人相关代码作为隐藏开关，除非用户重新明确改变决定。
- 不在未经备份、迁移预检和回滚演练的情况下直接改生产库。

## 4. 多智能体施工规则

### 4.1 开工前

1. 先提交当前 Prisma 多文件拆分，或把它合并成独立 PR。当前工作树有未提交改动，禁止其他 AI 直接在这里并行写文件。
2. 从同一个干净基线提交创建独立 worktree，每个任务包一个分支。
3. 每个 AI 开工先执行 `git status --short`、读取根 `AGENTS.md`、读取本计划和自己任务包涉及的文件。
4. 先写失败测试或可执行检查，再改实现；不允许只靠人工点击宣布完成。
5. 发现任务包外的问题，只记录，不顺手修复。

### 4.2 每个 AI 的固定输出

- 假设与不确定点。
- 变更文件列表及每个文件的必要性。
- 新增或修改的测试，以及修复前后结果。
- 数据库、API、环境变量、兼容性是否变化。
- 实际执行的命令和关键结果。
- 未解决风险和回滚方法。
- 一个或多个边界清晰的提交，不要混入格式化全仓库。

### 4.3 禁止事项

- 禁止 `git reset --hard`、覆盖别人的未提交修改、删除不理解的数据模型。
- 禁止编辑生成的 Prisma Client。
- 禁止在普通功能 PR 中新增 Migration。
- 禁止用字符串搜索测试代替行为测试。
- 禁止为了让 CI 绿色而删除、跳过或弱化失败测试。
- 禁止吞掉外部服务错误后返回空成功。
- 禁止在日志、测试快照、Issue 或 PR 中提交密钥与客户原始资料。

## 8. 任务包 WP-02：数据库和迁移只保留一个真源

**目标**：任何字段都能从 Schema 追到 Migration，从 Migration 追到生产状态。

**优先文件**：`prisma.config.ts`、`prisma/migrations/**`、`scripts/verify-production-schema.mjs`、`api/admin/migrate/route.ts`、`deploy.yml`。

**施工步骤**：

1. 删除 `prisma.config.ts` 的默认数据库 URL；执行迁移、diff、seed 时缺少 URL 必须 fail-fast。
2. 清点 `api/admin/migrate` 中每条 SQL 是否已有对应 Migration。
3. 对已覆盖 SQL，删除管理员迁移接口；对未覆盖 SQL，先补正式 Migration 和生产状态对齐说明，再删除接口。
4. 迁移流水线增加 `migrate status`、从空库重放、从生产结构快照 diff 三类检查。
5. 修复 build image 与 migrate 并行导致失败版本仍覆盖 `latest` 的问题；只有迁移和部署均成功后才推进稳定标签。
6. 为破坏性迁移建立 expand -> backfill -> switch -> contract 四阶段模板。
7. 添加迁移锁、超时和失败回滚 Runbook；禁止自动回滚已部分执行的破坏性 DDL。

**验收**：生产环境无裸 DDL API；缺少 `DATABASE_URL` 立即失败；空库可完整重放；生产 diff 无意外；失败发布不会污染稳定镜像标签。

## 9. 任务包 WP-03：API 运行时契约

**目标**：接口在进入 Service 前拒绝错误输入，并以稳定结构返回错误。

**目录原则**：契约放在 `src/features/aim/contracts`、`src/features/topics/contracts`、`src/features/competitor/contracts` 或对应领域；Route 只做鉴权、parse、调用 Service、映射响应。

**施工步骤**：

1. 生成 API 清单：method、route、auth、输入来源、输出、调用外部服务、费用等级、是否幂等。
2. 先覆盖登录、AIM chat/generate、知识上传、选题生成、竞品发现/刷新、Agent API。
3. 使用 Zod 为 JSON body、query、path params 和关键响应建立运行时 Schema；限制字符串长度、数组长度、文件大小和枚举。
4. 建立统一错误格式：`code`、`message`、`requestId`、可选 `field`；内部堆栈不下发客户端。
5. 统一 400、401、403、404、409、413、422、429、499、502、503、504 的语义。
6. 将请求 Schema 复用到前端 API Client 类型，但不让前端类型取代服务端校验。
7. 为旧 Agent API 保持版本兼容；破坏性变更只能进入新版本路由。

**验收**：所有写接口 100% 有运行时校验；关键 GET 有 query 校验；Fuzz/边界输入不会到达 Prisma；错误响应可被 UI 精确识别。

## 10. 任务包 WP-04：认证、会话与 Web 安全

**目标**：降低 Token 被窃取、管理员会话滥用和常见 Web 攻击风险。

**施工步骤**：

1. 将用户与管理员长期 Token 从 `localStorage` 迁到 `HttpOnly + Secure + SameSite` Cookie；设计兼容过渡和登出失效。
2. 管理员 Token 不再回退共用普通用户 Secret；管理员会话缩短并支持服务端撤销。
3. Cookie 鉴权的写请求增加 CSRF 防护；Bearer Agent API 保持独立认证。
4. 在应用或 Nginx 统一配置 CSP、HSTS、X-Content-Type-Options、Referrer-Policy、Permissions-Policy 和 frame 限制。
5. 登录、注册、激活、管理员登录增加账号/IP 组合限流、渐进退避和安全审计事件。
6. 检查富文本、Markdown、外链、图片代理和知识导入的 XSS/SSRF 边界。
7. 管理员高危动作加入审计记录：操作者、对象、动作、时间、requestId，不记录秘密值。

**验收**：浏览器脚本无法读取会话 Token；CSRF 测试通过；缺少关键 Secret 时启动/调用 fail-closed；安全头自动化检查通过。

## 11. 任务包 WP-05：多租户与资源授权

**目标**：彻底阻止用户通过猜 ID 读取或修改其他客户项目资料。

**施工步骤**：

1. 清点所有包含 `projectId`、`userId`、`generationId`、`sourceId`、`topicId`、`reportId` 的 Route。
2. 建立少量明确的授权 helper，如 `requireOwnedProject`、`requireOwnedGeneration`；不要创建万能 ACL 框架。
3. 查询条件尽量直接包含 owner，而不是先按 ID 查询后在内存判断。
4. AIM 任务单、知识、选题、竞品来源和上游生成记录必须重新按当前用户授权校验。
5. Agent API Key 绑定用户/项目/权限范围；密钥只显示一次，数据库只保存哈希。
6. 写跨租户负例测试：用户 A 的每类资源 ID 交给用户 B，必须统一返回 404 或 403。

**验收**：项目级 Route 授权覆盖率 100%；跨租户测试自动化；前端传入的事实和来源 ID 不被信任。

## 12. 任务包 WP-06：结构化可观测性与 SLO

**目标**：发生“发挥不稳定”时能定位是路由、上下文、模型、外部依赖还是 UI。

**施工步骤**：

1. 统一请求上下文：`requestId`、`runId`、匿名化 user 标识、projectId、workflowStage、routeId。
2. 用现有 Pino 替换关键链路 `console.*`；先改 AIM、topics、competitor、auth、migration、webhook。
3. 禁止记录完整 Token、密码、API Key、原始 Prompt、客户全文；必要内容只记 hash、长度、来源类型。
4. 将空 catch 分为：可忽略且有指标、可降级且对用户可见、必须失败三类。
5. 建立指标：成功率、P50/P95 延迟、超时率、fallback 率、空结果率、重试率、成本、队列积压。
6. `/healthz` 保持轻量 readiness；另建受保护的 dependency diagnostic，不把昂贵外部调用放进每次探针。
7. 为 AIM 生成、每日选题、竞品刷新、知识导入建立用户旅程 trace。

**验收**：随机抽取一个失败 run 能在 10 分钟内定位失败阶段；关键链路无裸 `console`；仪表盘可区分业务空数据和系统错误。

## 13. 任务包 WP-07：LLM 路由、成本与降级治理

**目标**：模型切换不再悄悄改变质量、成本和用户预期。

**施工步骤**：

1. 为 chat、generate、brief、quality、topic、competitor 建立显式模型策略：主模型、允许 fallback、超时、最大尝试、token 上限。
2. 非重试错误不得切模型；重试总时长和总尝试次数必须有上限。
3. 为单次任务、单用户每日、单项目每月增加 token/费用预算和告警；不要只记录使用量。
4. 上下文组装先做字符/token 预算，再按来源优先级裁剪；不得随机截断任务单关键约束。
5. 保存模型、版本、参数、Prompt hash、context hash、fallback 链，不默认保存完整敏感文本。
6. Harness 增加同一输入跨模型对比：路由一致、事实一致、格式一致、局部修改范围一致。
7. UI 明确显示“已使用备用模型/部分资料不可用”，而不是把降级结果伪装成正常结果。

**验收**：任一 run 可复现其策略；fallback 不超过预算；费用异常能被阻断；用户可见降级状态。

## 14. 任务包 WP-08：AIM 上下文、事实与 Prompt 注入防护

**目标**：让系统知道什么是事实、用户补充、模型推断和外部未验证线索。

**施工步骤**：

1. 为任务单和上下文片段保留来源类型、sourceId、owner、置信度、更新时间和授权状态。
2. 用户手动补充标记为 `user_claim`；知识库确认事实标记为 `confirmed`；搜索/竞品线索标记为 `pending_verify`。
3. 外部网页、竞品文案、上传文档都视为不可信内容，不得把其中指令提升为系统指令。
4. 任务单确认后的约束优先于模型建议；局部修改必须以结构化范围约束，而不是只靠自然语言提醒。
5. 上下文裁剪输出可解释清单：用了什么、没用什么、为什么。
6. Harness 增加 Prompt 注入、跨客户来源、事实冲突、资料不足、局部修改等对抗用例。

**验收**：模型不能把外部文本中的命令当系统命令；输出事实可追溯；资料不足时明确假设；未选区内容保持不变。

## 15. 任务包 WP-09：外部服务、Webhook 与后台任务韧性

**目标**：竞品、热点、OSS、飞书、微信、ASR、LLM 任一依赖波动时，不产生重复任务和假成功。

**施工步骤**：

1. 建立外部依赖清单：超时、重试、并发、幂等键、错误映射、降级、负责人。
2. 所有 fetch 必须有超时；重试只覆盖可重试错误，并使用指数退避和随机抖动。
3. Webhook 使用事件 ID/业务 ID 建立数据库幂等约束，Redis 仅作为加速层。
4. 创建任务与调用外部服务之间使用可恢复状态机；禁止“数据库已成功、外部调用丢失”无补偿。
5. 对耗时刷新、导入、生成建立明确 Job 状态；并发控制不依赖单进程内存。
6. 外部失败返回真实状态，不返回空数组 200；有缓存时标注缓存时间和数据新鲜度。
7. OSS URL 转存继续保持 SSRF 防护，并补 DNS 重绑定、响应流大小和 MIME 实测。

**验收**：重复 Webhook 不产生重复结果；Worker 重启后任务可继续；外部超时不会无限占用连接；用户能看到依赖降级。

## 16. 任务包 WP-10：客户失败恢复与信任体验

**目标**：用户不需要理解智能体和路由，也不会因为一次超时丢掉工作。

**施工步骤**：

1. 四阶段工作流每一步保存草稿、当前版本、来源、运行状态和下一步。
2. 所有长任务显示真实阶段：排队、读取资料、生成、质检、保存、完成；不能只显示一个无限 Loading。
3. 区分可重试错误、资料不足、权限失效、额度不足、外部服务不可用和系统错误。
4. 重试复用已确认任务单和已完成阶段，不重复扣费、不重复导入、不重复创建版本。
5. 每个结果页提供“本次使用依据”“未使用资料”“是否降级”“当前版本/历史版本”。
6. “只改开头/结尾/标题/选区”保存不可变范围快照并自动比较，超范围修改直接阻断。
7. 对每日选题和竞品发现提供可恢复缓存：旧数据可看，但清楚标注更新时间和刷新失败。

**验收**：断网、超时、刷新、返回上一页、重复点击等测试不丢稿、不重复任务；用户知道下一步该做什么。

## 17. 任务包 WP-11：数字人能力完整清除

**目标**：按用户决定删除数字人相关维护面，避免半删除。

**先清点后删除**：

1. 清点 Route、页面、组件、lib、类型、Prisma model/字段、环境变量、Worker、Cron、文档、测试、OSS 路径和第三方回调。
2. 重点检查 `avatars`、`voices`、`auth-video`、`public-avatar-previews`、Shanjian、任务重试中的 `virtualmanId/speakerId`。
3. 区分纯数字人能力和仍被其他视频流程复用的 OSS、Webhook、任务恢复代码。
4. 先移除前台入口与调用，再删除后端 Route/Service，再处理数据库字段与历史数据。
5. 若生产存在历史数字人数据，先导出数量和引用关系；Schema 删除走独立 Migration，不在同一提交硬删数据。
6. 删除文档中的数字人产品说明，防止后续 AI 按旧文档复活。

**验收**：代码、Route 列表、环境变量、测试、文档和生成客户端中无数字人残留；非数字人视频/内容流程回归通过。

## 18. 任务包 WP-12：查询、页面与成本性能

**目标**：用户量和历史数据增长后，页面与生成链路不会线性恶化。

**施工步骤**：

1. 审计 57 处 API `findMany`：分页、take 上限、索引、select 字段、排序稳定性。
2. 为 AIM 历史、知识库、竞品作品、选题池建立基于真实查询的慢查询基线。
3. 避免页面把完整历史、完整 Prompt 或大 JSON 一次性下发；详情按需加载。
4. 对知识检索、竞品推荐和选题生成记录输入规模、输出规模、DB 查询数和外部调用数。
5. 增加小规模并发压测，覆盖 AIM generate/chat、topics generate、competitor refresh。
6. 设置性能预算，但先测基线再定门槛；不凭感觉写 P95 数字。

**验收**：所有列表有硬上限；关键查询有索引证据；数据量放大 10 倍后无明显 N+1；成本与延迟回归可在 CI/预发发现。

## 19. 任务包 WP-13：隐私、留存、删除与灾备

**目标**：客户资料可控、可删除、可恢复，备份不是停留在“应该有”。

**施工步骤**：

1. 建立数据地图：账号、项目、知识、Prompt、生成稿、竞品、日志、OSS 文件、第三方副本。
2. 给每类数据定义用途、最小字段、留存期、访问角色、删除方式和备份范围。
3. AIM Harness 快照默认脱敏；只有诊断必需时保存完整内容，且访问受审计。
4. 实现账号/项目导出与删除流程，处理 DB 级联、OSS 对象、缓存、日志和第三方副本。
5. 建立数据库自动备份、OSS 生命周期、备份加密和恢复演练。
6. 先以 RPO 24 小时、RTO 4 小时作为待业务确认的临时目标，不能直接宣称已经满足。

**验收**：在预发完成一次从备份恢复；删除测试没有孤儿 OSS 和跨表残留；管理端访问敏感快照有审计记录。

## 20. 任务包 WP-14：供应链、分支与发布治理

**目标**：避免依赖漏洞、秘密泄露和未经审查的代码直接进入生产。

**施工步骤**：

1. 增加 CODEOWNERS，至少覆盖 Prisma/Migration、auth、AIM runtime、deploy、admin。
2. 对 `main` 开启必需检查和禁止直接 push；要求至少一个审查者。
3. CI 增加依赖审计、Secret Scan、SAST、容器镜像扫描和 SBOM 产出。
4. 固定 Node、pnpm、Prisma 和基础镜像版本；依赖升级由独立 PR 执行。
5. 镜像使用不可变 SHA 标签；`latest` 只在发布成功后更新。
6. 建立 staging -> canary -> production 流程；数据库 Migration 与应用回滚兼容。
7. 发布后执行真实用户冒烟，不只检查 DB/Redis。

**验收**：未通过必需检查不能合并；泄露测试 Secret 能被阻断；高危依赖有处理 SLA；失败发布可回滚应用且不破坏数据。

## 21. 任务包 WP-15：领域边界和长期维护

**目标**：未来迭代继续演化，而不是几年后重新长成大泥球。

**目录规则**：

- `src/features/aim`：工作流、动作、上下文、版本、UI 组件、领域 Service。
- `src/features/topics`：选题来源、候选、日报、聊天和 UI。
- `src/features/competitor`：监控账号、发现、刷新、报告和 UI。
- `src/app/**/page.tsx`：加载、组合、路由级状态，不放推荐算法和数据访问。
- `src/app/api/**/route.ts`：鉴权、输入校验、Service 调用、响应映射。
- `src/lib`：真正跨领域且稳定的基础设施；不得成为所有业务的默认落点。

**施工步骤**：

1. 保持当前源码 500 行、Prisma 400 行防线；新增豁免必须写原因、负责人和到期日。
2. Architecture Guard 增加禁止页面直接访问 Prisma、禁止 Route 写大段业务流程等边界规则。
3. 每个领域建立一个短 README：入口、公开 Service、数据所有权、事件、依赖、禁止引用方向。
4. 新能力先落领域目录；历史大文件只在被修改时顺带拆出本次新增部分，不集中返工。
5. 清理重复 Client、错误映射和工具函数时，以行为测试证明等价。

**验收**：新增功能不增加跨领域反向依赖；页面/Route 维持薄层；Architecture Guard 对故意违规样例能失败。

## 22. 任务包 WP-16：全链路验收与灰度

**目标**：从“代码通过”升级为“真实客户流程可用”。

**必须覆盖的客户旅程**：

1. 新用户注册、激活、进入 AIM。
2. 定方向生成任务单，确认后写稿。
3. 直接新写、局部修改、对标重写、拆多平台。
4. 知识导入后生成，验证来源与权限。
5. 选题日报生成失败、恢复、换选题、进入 AIM。
6. 竞品账号发现、添加监控、刷新、失败降级、进入拆解或写稿。
7. 发布前质检、发布登记、复盘沉淀。
8. Agent API 旧版本调用和错误兼容。
9. 管理员查看运行记录，但看不到越权客户资料。
10. 删除项目/账号后验证数据生命周期。

**灰度步骤**：

1. 预发从生产脱敏快照恢复并执行迁移。
2. 跑完整门禁、依赖诊断、性能基线和安全冒烟。
3. 只给内部账号和少量项目开启新链路。
4. 观察成功率、P95、fallback、空结果、重试、整篇重写、发布后复盘和投诉。
5. 达到事先批准的门槛后逐步扩容；异常立即关闭功能开关或回滚应用。

**验收**：连续观察周期内无跨租户、数据丢失、重复扣费和不可恢复任务；关键体验指标不低于旧版本。

## 23. 固定验证命令

执行智能体应从仓库根目录确认实际脚本后运行，不能擅自把失败步骤删掉：

```bash
pnpm install --frozen-lockfile
pnpm --dir apps/web exec prisma validate
pnpm --dir apps/web exec prisma generate
pnpm --dir apps/web run typecheck
pnpm --dir apps/web run lint
pnpm --dir apps/web run arch:size
pnpm --dir apps/web run arch:check
pnpm --dir apps/web run test:harness
pnpm --dir apps/web run test
pnpm --dir apps/web run build
pnpm --dir apps/web run env:check
pnpm --dir apps/web run schema:migration-status
```

需要数据库或浏览器的测试必须在隔离环境执行，并记录数据库地址类别、迁移版本、浏览器版本和测试数据种子；严禁在文档中记录真实密码。

## 24. 合并顺序与冲突边界

推荐合并顺序：

1. Prisma 多文件基线。
2. 测试门禁。
3. 数据库单真源。
4. 数字人清除的非 Schema 部分。
5. 数字人 Schema Migration。
6. API 契约基础类型。
7. 鉴权与会话迁移。
8. 多租户授权。
9. 统一事件与日志上下文。
10. LLM/AIM/外部依赖/UX 各领域改动。
11. 发布、供应链、灾备和最终灰度。

同一波次即使并行开发，也不能同时合并多个会修改 `env.ts`、`deploy.yml`、`prisma/**`、鉴权 wrapper 或 AIM 核心契约的 PR。先选一个基础 PR 合并，其他分支 rebase 后重新跑完整验证。

## 25. 给每个执行 AI 的投喂模板

```text
你只执行《AIM 仓库可靠性与客户体验治理主计划》的 WP-XX。

开工要求：
1. 读取仓库根 AGENTS.md、主计划和相关源码。
2. 报告 git branch 与 git status；不要覆盖任何未提交改动。
3. 明确假设、成功标准、允许修改文件和明确不修改的文件。
4. 先写能复现风险的测试或检查，再做最小实现。
5. 不执行其他任务包，不顺手重构，不新增无需求抽象。
6. 涉及 Schema、Migration、鉴权、公开 API 时，必须列兼容与回滚方案。
7. 完成后运行任务包验收和仓库固定门禁。
8. 输出：变更摘要、文件清单、测试证据、剩余风险、提交 SHA。

如果当前基线、文件或行为与主计划不一致，停止修改，先报告差异；不要静默采用自己的解释。
```

## 26. 主控 AI 的职责

主控 AI 不替执行 AI 重做全部代码，只负责：

1. 冻结共同基线和任务包边界。
2. 审核每个 PR 是否越界、是否弱化测试、是否引入重复抽象。
3. 维护风险表、依赖图、迁移顺序和合并队列。
4. 每合并一个基础 PR，通知其他分支 rebase 并重新验证。
5. 汇总端到端证据，决定是否进入灰度；不得用“构建通过”替代上线判断。

## 27. 最终停止条件

出现以下任一情况，必须停止合并或上线：

- 全量测试仍有无法解释的失败或挂起。
- 生产 Schema 与 Migration 不一致。
- 迁移没有备份、回滚或兼容窗口。
- 任一关键 Route 存在跨租户读取/修改。
- 认证 Secret 缺失时系统仍能以默认值运行。
- 用户输入或客户资料出现在公开日志、错误响应或无权限快照中。
- fallback、重试或重复点击可能造成重复扣费/重复任务。
- 数字人删除导致非数字人内容流程回归失败。
- 新版本关键旅程成功率或恢复能力低于旧版本。

这份计划的核心判断是：AIM 下一阶段不能继续靠“功能加完再整体测试”。先把真源、契约、权限、可观测性和恢复机制建立起来，后续每次迭代才会越来越快，而不是功能越多、发挥越不稳定。

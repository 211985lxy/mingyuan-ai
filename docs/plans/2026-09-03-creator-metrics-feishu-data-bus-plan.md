# 创作者数据飞书总线接入方案（Creator Metrics Feishu Data Bus）

> 状态：草案（待评审） · 日期：2026-09-03 · 类型：分析型方案文档，确认后另立实施工作包
> 上游工具：[Xavier-168/data-scientist-community](https://github.com/Xavier-168/data-scientist-community) v0.1.0-rc.2

## 1. 背景与业务目标

内容增长闭环为「客户问题 → 选题 → 内容 → 发布 → 数据复盘」。当前复盘环节存在断点：

- `aim-weekly-review` 的指标（`publishedCount` / `qualifiedLeadCount` / `appointmentCount` / `dealCount` / `revenue`）依赖人工回填，存在 `day7Backfill` 催填机制。
- 用户自己账号在抖音 / 小红书 / B 站 / 快手的真实播放、阅读、互动数据没有任何自动进入 AIM 的通道。
- 复盘 Agent 缺乏真实表现数据，无法做「哪类选题真实带来了流量与线索」的归因。

**业务目标**：让用户的平台作品表现数据自动流入 AIM，喂给数据复盘，把周度复盘从「人工填数字」升级为「真实数据 + AI 归因」。

**成功判据**：一名种子用户配置完成后，其周度复盘报告中出现自动读取的四平台作品表现指标，且全程无人工回填。

## 2. 选型结论与硬边界

### 2.1 为什么是「飞书数据总线」而不是代码集成

上游工具为 **AGPL-3.0-only** 双重许可（社区版 AGPL，闭源商用需向作者单独购买，其商业合同仍在律师审阅阶段）。AGPL 具强传染性：其代码一旦进入 AIM 闭源产品并以网络服务提供，组合作品面临整体开源义务。

**硬规则：**

- ❌ 禁止将该项目的任何源码（含脚本、normalizer、配置）复制进 mingyuan 仓库。
- ❌ 禁止 fork 后改头换面并入（同为衍生作品）。
- ✅ 允许对接其**输出数据**（飞书多维表格 / Excel）——数据与字段格式不受许可证约束。
- ✅ 允许参考其公开架构思路自研（Playwright + 用户浏览器 Profile + 各平台 normalizer），但自研实现不得抄写其代码。注意 MediaCrawler 为非商业许可，同样不可抄。

### 2.2 备选方案对比

| 方案 | 许可证风险 | 工程量 | 实时性 | 结论 |
| --- | --- | --- | --- | --- |
| A. 飞书多维表格总线 | 无 | 低（复用现有 lark-base） | 随上游同步（用户触发） | **采用，P0-P1** |
| B. Excel 手动导入 | 无 | 极低 | 无 | 仅作 P0 验证 fallback |
| C. 自研采集 sidecar | 无（需 clean room） | 高 | 最高 | 数据复盘被验证为核心卖点后再启动 |

## 3. 上游工具事实清单（以 2026-09-03 README 为准）

- 形态：Python 3.11+ 编排 + Playwright 复用用户本机浏览器 Profile，采集抖音 / 小红书 / B 站 / 快手创作者后台。
- 平台支持：仅 macOS 11+（Windows 在计划中）；Node >=22.12 <23。
- 对外接口：**无 HTTP API / MCP**，仅有绑定 `127.0.0.1:8811` 的本地页面。唯一结构化输出口为飞书多维表格同步（用户提供 App ID / Secret 与目标表）。
- 数据口径：统一作品字段、日期、播放 / 阅读指标，过滤无效零值记录；保留平台来源字段。
- 成熟度：v0.1.0-rc.2，22 star，17 commits，单人维护。**定位为"推荐用户自装的本地工具"，不得成为 AIM 的运行时依赖。**
- ✅ **飞书表结构已核实**（2026-09-03，上游单一事实源 `scripts/domain/feishu_schema.py`，见第 4 节）：同步时自动创建多维表格与 5 张数据表，中文字段、带 upsert 主键，写入语义为按主键覆盖（非追加快照）。

## 4. 飞书数据总线结构（上游已定义，AIM 侧做映射）

> 2026-09-03 已核对上游 `scripts/domain/feishu_schema.py`（v0.1.0-rc.2，prepare 与 sync 共用的单一事实源）。上游飞书同步会**自动创建**多维表格（base）与 5 张数据表，无需我方设计建表。

上游 5 张表概览：

| 数据表 | upsert 主键 | 语义 | AIM 是否读取 |
| --- | --- | --- | --- |
| 平台明细V2 | 平台作品键 | 单平台单作品当前指标 | ✅ 主数据源 |
| 作品总表V2 | 同步键 | 跨平台聚合后的作品总指标 | ✅ 复盘汇总 |
| 作品增量表 | 同步键 | 对比上一快照的增量、日均增量 | ✅ 趋势归因 |
| 作品图表表 | 同步键 | 日期 × 平台指标矩阵 | P2 视需要 |
| 同步日志V2 | 批次同步键 | 每批次同步记录数、新增作品数、备注 | ✅ 数据新鲜度 |

`平台明细V2` → AIM `creator_posts` 字段映射（平台单选选项：抖音 / 小红书 / B站 / 快手）：

| AIM 字段 | 上游字段（类型） |
| --- | --- |
| platform | 视频平台（单选） |
| post_id | 平台作品键（文本，upsert 主键） |
| title | 视频标题 |
| published_at | 视频发布日期（日期） |
| views | 总流量（数字） |
| likes / comments / shares / collects | 点赞量 / 评论量 / 分享量 / 收藏量（数字） |
| followers_delta | 涨粉量（数字） |
| quality（新增可用，送复盘归因） | 完播率、点赞率、评论率、分享率、收藏率、封标点击率、3s跳出率（数字） |
| collected_at | 不逐行取；以 `同步日志V2` 的「同步日期」作为数据截止时间 |

设计要点（依上游事实修正）：

- 写入语义为 **upsert（按主键覆盖）+ `prune_missing_records`**：平台明细只保留当前有效作品，不是追加快照。历史趋势不自建快照表，直接读上游 `作品增量表` / `作品图表表`。
- 字段名是上游稳定契约（`feishu_schema.py` 单一事实源）；AIM 侧映射集中收在 `lib/api/creator-metrics.ts` 一个模块，上游变更只改映射层。
- 上游同步字段中**没有作品链接**；如需要，从平台作品键拼装，或向对方提 feature。
- 敏感边界不变：表中无 Cookie / 登录态，仅作品级指标。

## 6. 数据流与同步策略

```
用户本机: data-scientist-community（用户自行安装、自己账号登录）
   └─(用户触发/定时)→ 飞书多维表格（上游自动建表：平台明细V2 / 作品总表V2 / 作品增量表 等 5 张）
        ↑ AIM 不主动拉取平台，不持有用户 Cookie
AIM 后端: /api/aim/creator-metrics
   └─ 读取总线表 → 字段映射 → 周期聚合 → weekly review / 复盘 Agent
```

- 拉取时机：用户打开复盘页时按需拉取 + 服务端 15 分钟缓存；不做后台轮询（P0/P1 阶段）。
- 缺数据降级：总线表为空或未配置时，复盘页回退现有人工回填流程，并给出配置引导卡片（含上游工具安装指引链接），**不得返回假数据或静默空转**。
- 上游工具的安装与飞书配置文档放 `docs/guides/`，明示：工具由第三方提供、跑在用户本机、账号风险由用户自担。

## 7. 风险登记

| 风险 | 等级 | 缓解 |
| --- | --- | --- |
| 上游项目停更 / 破坏性变更 | 中 | AIM 只依赖「飞书多维表格」这一输出形态；字段契约收在映射模块，替代写入方（Excel 导入、自研采集）对齐同一映射即可切换 |
| 上游仅 macOS | 中 | 文档明示平台限制；Windows 用户走 Excel 导入 fallback |
| 自动化访问创作者后台的平台条款风险 | 中 | AIM 不执行采集、不碰 Cookie；措辞上不承诺"不被风控" |
| 用户误以为 AIM 官方背书该工具 | 低 | 指引文档声明第三方独立项目 |
| 上游字段映射失败 | 已消除 | 2026-09-03 核对 `feishu_schema.py`，映射见第 4 节；上游大版本变更时仅改映射模块 |
| 复盘语义混淆（人工 vs 自动指标） | 低 | UI 分区 + 数据来源徽标 |

## 8. 里程碑

- **P0 价值验证（1-2 天）**：内部（老板本人账号）装上游工具 → 真实同步一次（上游自动建表）→ 人工核对 5 张表数据正确性 + AIM 侧按第 4 节映射做一次读取冒烟。产出：真实表链接与读取冒烟结论（字段映射已于 2026-09-03 预先核对，见第 4 节）。若验证失败，止损于此，不影响 AIM 现有功能。
- **P1 最小集成（一个工作包）**：完成第 5 节改动，weekly review 出现真实平台指标。集成层验收必须用 P0 的真实表跑通读取、字段契约与空表降级。
- **P2 复盘智能化（独立工作包）**：复盘 Agent 消费 `platformMetrics` 做选题归因（哪类选题带来播放/线索）、输出改进建议；视效果决定是否启动方案 C 自研采集。

## 9. 验收标准（四层）

1. **代码层**：新增模块单测覆盖快照去重与周期聚合边界（跨平台、同作品多快照、空表）；类型、Lint、架构与体积门禁通过。
2. **构建层**：涉及 API 路由与环境变量，必须通过生产构建。
3. **集成层**：用 P0 真实总线表验证读取、权限、字段契约；验证未配置/空表时降级路径返回配置引导而非报错或假数据。
4. **上线层**：从明确 commit 部署后，种子用户真实账号完成一次「同步 → 打开周度复盘看到自动指标」的端到端冒烟。

## 10. 开放问题（评审时定）

1. 总线表按用户隔离（上游按用户自己的飞书 App 自建 base，天然每用户一张）；P1 需确定 AIM 侧 per-project 的 base app_token / 表 ID 存放位置（项目配置 vs 全局 env）。
2. `platformMetrics` 进入复盘后，人工回填的 `publishedCount` 是否保留双轨？初步倾向保留双轨一个周期后评估。
3. P2 的选题归因需要作品 ↔ AIM 选题卡的关联键（如发布时在简介/置顶评论埋 ID），是否可行需单独评估。

# 分支与候选版本治理

## 目的

解决“在错误分支继续开发、工作完成但没有进入候选版本、重复合并已有能力”三个问题。真实状态以 Git 和 `.release-control.json` 为准，不以聊天记录、静态分支数量或计划完成标记为准。

## 唯一候选原则

- 当前候选发布分支只有一个：由 `.release-control.json` 的 `candidateBranch` 声明。
- `main` 是目标分支，不是日常开发分支。
- 其他分支是功能输入或历史证据，默认只读。不能因为它出现在清单里就整分支合并。
- 候选分支应从覆盖面最完整、门禁最强的已审查基线建立，再选择性移植其他分支的独有改动。

## 发布或收敛任务开工

1. 读取根 `AGENTS.md`。
2. 运行 `pnpm release:context`。
3. 查看 `git status --short`，隔离无关改动。
4. 用 `git log --left-right --cherry-pick` 或等价方式确认来源分支真正独有的提交。
5. 为本次工作包声明目标、文件范围、不做项和验收条件。

`pnpm release:context` 不通过时停止发布/合并工作。普通功能开发可以在独立分支进行，完成后由审查者决定是否移植到候选分支。

## 合并决策

对每个来源提交只允许三种结论：

- **移植**：业务价值明确、与候选架构兼容，并有对应测试。
- **改写后移植**：目标正确，但旧实现会覆盖新版架构、产生误报或缺少契约。
- **暂缓/拒绝**：改变运行行为却缺少评估，涉及 Schema 却缺少迁移证据，或只是流程/文档表面完成。

不得用“逐分支 merge + 每次修冲突”的方式处理共享大量提交的分支体系，这会把重复历史和过期实现重新带回候选版。

## 发布门禁

候选版本至少需要：依赖锁定、Prisma 验证与生成、环境契约、API 清单、依赖安全审计、应用和测试类型检查、Lint、架构守卫、全量单测、Harness、生产构建。涉及数据库或飞书等外部系统时，还必须完成隔离数据库 E2E、迁移状态和最小真实样本联调。

门禁通过后记录明确 commit SHA。部署、回滚和线上验证都围绕该 SHA，不使用“最新分支”作为发布身份。

## 回滚

- 尚未合并：保留来源分支和候选分支，停止移植即可。
- 已合并未部署：使用 `git revert` 生成可审计的反向提交。
- 已部署：优先部署上一已验证 SHA；若涉及 Schema，必须先确认向后兼容和迁移状态。
- 禁止在共享工作区使用 `git reset --hard` 作为标准回滚方式。

## 当前已知限制

若 `pnpm release:context` 显示 `remoteBackup=missing`，说明提交仍只有本地副本。可以继续本地审查，但在配置并验证远程备份前，发布结论最多为“有条件通过”。

# AIM 生成可靠性、指令忠实度与历史持久化升级计划 V2

**目标文件：** `docs/superpowers/plans/2026-09-07-aim-generation-reliability-deep-repair-v2.md`

## 一、问题归类与优先级

| 问题现象 | 可能原因 | 优化建议 | 优先级 |
|---|---|---|---|
| 用户未要求“两分钟、400–550字”，系统却自行加入 | 历史任务、模板、方法论或提示词默认值覆盖当前指令 | 建立唯一指令优先级；未明确指定的时长、字数、数量、CTA一律不得推断 | 高 |
| 给了参考文案后，Agent揣错用户真正要做的事 | 参考资料与当前要求未结构化分离；语义分类结果反向控制用户指令 | 当前用户要求作为唯一控制源；参考文案只能提供事实、结构和风格，不能定义任务 | 高 |
| 返回思考过程、工作步骤或分析说明，没有生成最终文案 | 生成正文、内部推理、客户可见思考依据共用同一输出通道 | 建立统一交付闸门：必须先有完整成品；只允许另行展示简化的“思考依据”，禁止原始思维链进入正文 | 高 |
| 内容创作、商业诊断显示“这次没有完成” | 单供应商超时、空正文、调用链重复计算、总截止时间不统一 | 统一115秒服务端截止时间，并按不同供应商降级；最多实际调用3个供应商 | 高 |
| 从爆款拆解进入文案创作，提交后退出页面，任务和聊天记录消失 | 只有生成成功后才创建 `AimGeneration`；失败、超时、澄清阶段没有可恢复任务记录 | 用户点击生成后立即创建任务；成功、失败、等待补充都更新同一记录，刷新或退出后仍能恢复 | 高 |
| 失败后前端自动再次发送，重复等待、重复扣费 | 客户端把服务端错误误判为可安全重试 | 网络层重试与用户主动重试分开；服务端已接收后禁止静默重跑 | 高 |
| 所有失败都提示“补充一句要求” | 后端没有稳定错误码，前端无法区分模型故障、指令缺失和额度问题 | 统一错误分类和对应操作，不把供应商故障说成用户要求不清楚 | 中 |
| Trace停留在运行中，无法复盘真实失败环节 | 异常、澄清、普通回复等分支没有统一结束 Trace | 所有终止分支收口；10分钟以上悬挂执行自动标记失败但不删除 | 中 |

**执行顺序：** 先修“当前指令唯一真源”，再建立“用户任务立即落盘”，然后修交付闸门和模型降级。原因是后续测试产生的失败、重试和降级，都必须先有稳定任务身份才能被可靠追踪和恢复。

## 二、实施方案

### 1. 收敛现有执行分支

- 保留已完成提交 `66597209`，将其作为“当前指令唯一控制源”的基线。
- 当前分支已有截止时间和模型路由测试改动，先保护现有工作，不重置、不覆盖。
- `96a6ccba` 仅作为历史持久化实现参考，不直接 cherry-pick；其中与当前路由、项目绑定和统一执行服务重叠的部分必须手工移植。
- 特别保留 `resolveBoundProject` 的账号项目绑定校验，不能因移植历史补丁而绕过项目隔离。
- 单一工作树顺序实施，每项独立提交；生产部署不包含在本计划的默认授权内。

### 2. 当前用户指令成为唯一真源

- `sourceEnvelope` 明确拆分为：当前要求、当前素材、参考资料、相关历史和方法论。
- 固定优先级：当前明确要求 ＞ 本任务已确认要求 ＞ 当前素材事实 ＞ 项目资料/历史/方法论。
- 新任务默认切断旧任务的时长、字数、数量、形式、CTA和用途；只有出现“这篇、上一版、继续、保持刚才时长”等明确引用才允许继承。
- 参考文案中的“2分钟、6分半、22个镜头”等内容默认视为参考案例事实，不得转化成本次交付规格。
- 只有真正影响成品的缺口才追问，一次最多3项；可以直接按用户要求交付时不得先输出任务分析。

### 3. 建立统一生成任务生命周期

共享任务服务同时覆盖内容创作、商业诊断及其规范别名，不只修复 `content_producer` 单一路由。

- 用户只是从爆款拆解进入创作页并完成预填时，不创建历史记录。
- 用户点击“生成/发送”且通过认证、额度、请求格式及绑定项目校验后，立即创建 `AimGeneration`，再进行语义分析和模型调用。
- 生命周期统一为：

  `pending → running → awaiting_input / completed / degraded / failed`

- 生成成功必须更新原记录，禁止再创建第二条成功记录。
- 生成失败、超时、空正文、供应商不可用时，保留原始提交内容、目标格式、项目、Agent、状态和脱敏错误。
- 生成任务需要澄清时保留为 `awaiting_input`，退出后可从侧栏重新打开并继续补充。
- 纯咨询或普通聊天被判定为 `reply` 时不写入作品历史，避免普通聊天污染任务列表。
- 传输层重复请求携带同一 `attemptId`：已完成则返回已有结果，运行中返回 `GENERATION_IN_PROGRESS`，失败则返回原失败状态，不重复调用模型。
- 用户点击“再试一次”才允许重新执行同一任务，并将新运行写入 Trace/Snapshot；修改了核心要求则创建新任务。
- 10分钟仍为 `pending/running` 的任务转为 `failed/STALE_EXECUTION`，保留记录供恢复和审计。

### 4. 建立最终交付闸门

- 所有口播、原始文案、商业诊断、文章和派生格式统一经过交付检查。
- 正文不得包含“我将分析、以下是思考过程、任务理解、让我检查、生成计划”等内部过程。
- “思考依据”只展示目标、采用的资料、关键取舍、必要假设和风险提醒，并放在独立折叠区域；不进入复制内容。
- 仅有分析而没有成品、正文为空、包含未授权规格或泄露内部推理时，判定为交付失败。
- 闸门最多触发两次定向修正；仍不合格时返回 `DELIVERY_CONSTRAINT_VIOLATION`，不得把思考过程当作答案交付。
- 用户没有指定时长、字数、数量时，交付闸门同时检查正文中是否出现系统自行添加的硬规格。

### 5. 统一截止时间、供应商降级和错误处理

- 服务端共享总截止时间115秒，客户端等待上限120秒；嵌套调用不得重新获得完整时间预算。
- 质量优先顺序（2026-09-08 修订）：Claude → Doubao（火山方舟旗舰，国内直连低延迟）→ APIMart GPT-5.4；DeepSeek仅作为紧急替补。
  - 修订原因：GLM 自计划确立以来从未配置 API Key（探测为 unconfigured），第二跳实际空转；Doubao 复用账号现有 ARK_API_KEY，国内端点无需代理。
  - 前置条件：需在火山方舟控制台开通对应旗舰模型；未开通时该跳快速失败并被熔断跳过，不影响链路。
- 单次任务最多实际调用3个不同供应商；同一供应商的多个模型不得伪装成多供应商降级。
- 超时、429、5xx、空正文和可恢复解析失败允许切换下一个供应商；用户主动停止、请求无效和账号项目错误不降级。
- 增加短时熔断，连续故障的供应商暂时跳过；部署前必须做真实供应商探测。
- 稳定错误码至少包括：`INVALID_REQUEST`、`BOUND_PROJECT_UNAVAILABLE`、`MODEL_TIMEOUT`、`PROVIDER_UNAVAILABLE`、`PROVIDER_AUTH`、`PROVIDER_QUOTA`、`EMPTY_OUTPUT`、`DELIVERY_CONSTRAINT_VIOLATION`、`GENERATION_IN_PROGRESS`、`STALE_EXECUTION`、`USER_ABORTED`、`INTERNAL_ERROR`。
- 供应商错误只在管理员记录中保留；客户端显示可理解的原因和正确操作。

## 三、接口与数据调整

- 生成请求增加可选 `attemptId`，格式固定为 `web_` 加24位十六进制字符；旧客户端不传时由服务端生成，保持向后兼容。
- 生成、澄清和失败响应统一返回可用的 `runId`；请求被系统接收后同时返回 `generationId`。
- 错误响应统一为 `{ error, code, runId?, generationId? }`。
- `AimGeneration` 复用现有 `status`、`errorMessage`、`rawInput`、`taskSpec` 字段，不新增任务表；`taskSpec.execution`保存等待补充、重试和来源状态。
- 仅新增 `AimExecutionTrace.errorCode` 可检索字段；每次供应商尝试继续写入现有 `AimRunSnapshot.providerAttempts`。
- 历史接口必须返回没有成品正文的 `running`、`awaiting_input` 和 `failed` 记录；前端映射不得因为 `results` 为空而丢弃任务。

## 四、测试与验收

- 指令回归：历史含“2分钟、400–550字”，当前未提长度时不得继承；当前明确要求保持时才继承。
- 参考资料回归：对标案例中的时长、产品、人物和动作不得被误当成本次命令。
- 交付回归：仅输出分析、思考过程、任务计划或内部自检时必须被拦截；客户可见思考依据与正文严格分离。
- 历史回归：从爆款拆解进入创作，提交后分别模拟成功、模型超时、空正文、等待补充、刷新、关闭页面和重新登录，任务都能从侧栏恢复。
- 幂等回归：相同 `attemptId` 的网络重试只产生一条任务、一个有效执行，不重复调用模型；用户主动重试可产生新运行记录。
- 项目隔离回归：不同账号、项目或不同请求内容复用同一 `attemptId` 时必须拒绝，不能读取或覆盖其他任务。
- 故障注入：Claude超时后Doubao成功、Claude空正文后Doubao成功、前两路失败后第三路成功、三路全失败、供应商熔断、总截止时间到期、用户停止。
- 完整门禁：相关单测、151条AIM Harness、类型检查、架构检查、API契约、数据库边界和生产构建全部通过；已有无关基线失败必须单独登记，不得伪装成本次通过。
- 内部灰度至少20条真实任务，包含内容创作、对标改写、全文润色、商业诊断及爆款拆解进入创作。
- 上线门槛：成功率至少19/20，P95不超过120秒；隐藏时长、思考泄漏、历史丢失、重复模型调用、10分钟悬挂任务均为0。
- 获得部署授权后才执行生产发布；发布后观察24小时，未达到成功率95%或出现历史丢失、串项目、重复扣费时立即停止扩大使用并回滚应用版本，保留兼容字段和失败记录。

## 五、完成标准与默认约定

- 用户说什么，当前任务就以什么为准；模板、历史和参考资料不能改变任务。
- 未指定的长度、数量、形式和CTA不由系统自行补充。
- 每次生成先有可恢复任务，再开始模型调用；失败也能在侧栏找到并重新打开。
- 任何可交付结果必须包含成品正文；客户可见思考依据不能替代成品。
- 供应商故障能在120秒内降级成功或给出准确、可恢复的失败结果。
- 前端不再静默重放已被服务端接收的生成请求。
- 本次不新增工作流、不增加新Agent、不重构账号体系、不展示原始思维链，也不直接执行生产部署。

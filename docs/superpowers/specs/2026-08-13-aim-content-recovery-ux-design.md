# AIM 内容生成失败恢复体验设计

## 目标

当语义任务理解模型返回不完整协议时，系统先自动恢复；最终仍失败时，只展示对用户有意义的状态，不暴露“协议不完整”等内部实现信息。已经生成的正文、事实核验提醒和系统失败状态必须分层展示，避免用户把审核备注当成正文。

## 范围

- 服务端语义理解增加一次格式修复重试，不重复执行正文生成。
- 无法恢复时保留原始错误到 trace，接口仅返回友好文案。
- 失败消息使用独立状态卡，不再渲染成普通正文。
- 内容安全提醒继续显示在交付物上方，不混入可复制正文。
- 不改 AIM 四步工作流、不重做聊天页面、不新增数据库字段。

## 数据流

1. 用户提交生成请求。
2. 语义理解第一次返回结果；解析成功则继续。
3. 解析失败时，用同一模型和原始输出发起一次“只修复协议格式”的请求。
4. 修复成功则继续原任务；修复失败则记录技术错误，接口返回“这次没有完整理解你的要求……”的用户文案。
5. 前端把失败渲染为紧凑状态卡，并提供“再试一次”；不把失败文本当作生成正文。

## 展示规则

- 正常回复：沿用 Markdown 正文展示。
- 正常交付物：正文卡片保持可编辑、可复制。
- 内容核验：独立琥珀色提示，明确“不会复制进正文”。
- 请求失败：独立浅灰/琥珀状态卡，标题“这次没有完成”，说明当前稿件已保留，并显示“再试一次”。
- 禁止出现：语义理解协议、解析、模型、JSON、provider 等内部术语。

## 验收

- 第一次协议缺失、第二次修复成功时，语义理解函数返回成功且调用模型两次。
- 两次均失败时，服务端错误映射不向用户暴露内部中文错误。
- 失败消息不再经过 Markdown 正文渲染，页面包含“这次没有完成”和“再试一次”。
- 核验提示与正文 DOM 分离，并明确不会复制进正文。

# AIM 日常对话与内容工作流分流设计

## 决策

AIM 必须先判断用户是在正常交流，还是明确要求产出或修改内容。

- 日常讨论、解释、评价、确认需求、追问原因：直接正常回答。
- 明确要求写作、改写、编辑或生成作品：进入内容执行工作流。
- 真正缺少完成创作所必需的信息：只针对缺口追问。

岗位卡和 Skill 用来完成内容任务，不得成为所有对话的前置门槛。

## 当前问题

现有快速分流把“输入较长”当成“用户要创作”。当普通讨论超过固定字数时，系统会错误进入交付流程，再要求用户补充内容目标、受众等字段。这会造成两个直接问题：

1. 用户只是在讨论方案，却被迫填写任务卡。
2. 系统看起来听不懂上下文，只会推进固定流程。

此外，普通回复路径没有完整使用已经收集的最近对话和参考材料，多轮交流容易丢失语境。

## 目标行为

### 普通对话

以下请求直接回答，不触发工作流缺口检查：

- “这个流程是不是太复杂了？”
- “流量型、线索型和信任型应该怎么分？”
- “你刚才这句话是什么意思？”
- 对已有方案的讨论、评价、补充和确认。

回复时可使用当前用户原话、最近相关对话、当前作品和相关参考材料，但不得把历史内容误当成新任务。

### 内容交付

只有当前用户明确提出创作或编辑动作时，才进入统一内容执行，例如：

- “按下面材料写一条口播稿。”
- “把这篇文章改成小红书图文。”
- “重写第二段，其他部分不要动。”

进入交付路径后，仍沿用现有语义理解、必要澄清、生成、验收和交付机制。

### 真正澄清

澄清只用于影响结果且无法从上下文判断的关键缺口。不能因为消息长、字段不齐或尚未建立完整任务卡，就阻止普通交流。

## 实现范围

1. 删除“正文或请求达到固定字数就直接判定为交付”的快速规则。
2. 保留明确创作请求的快速交付，以及明确分析问题的快速回复。
3. 其余请求交给现有语义理解器判断，不新增关键词分类体系。
4. 普通回复路径加入有边界的最近对话、当前作品和相关参考材料。
5. 工作流缺口检查只约束交付或澄清，不约束普通回复。

## 不做

- 不改变选题官、文案创作官、作品编辑官、数据复盘官的职责。
- 不新增聊天 Agent 或发布 Agent。
- 不改数据库结构、版本记录或前端页面布局。
- 不用新的字数阈值替代旧阈值。
- 不允许普通聊天绕过真正内容交付所需的事实与安全检查。

## 验收标准

1. 超过 120 字的普通讨论不会仅因长度进入交付流程。
2. “按材料写一条口播”等明确创作请求仍进入交付流程。
3. “分析这段内容的问题”等分析请求仍直接回答。
4. 普通回复能够读取最近相关对话及当前作品，不再只看本轮一句话。
5. 普通回复不会弹出任务卡、目标用户或内容目标的固定追问。
6. 现有统一内容执行与语义验收测试保持通过。

## 回滚方式

本次只调整分流与普通回复上下文。若上线后出现误判，可按单个提交回滚，不涉及数据迁移。

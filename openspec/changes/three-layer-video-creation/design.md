## Context

这次 change 不是给现有页面再加一个下拉框，而是要把 ClipFlow 的视频生成中枢从“单层向导”升级成“多层生产系统”。

当前系统暴露出 5 个核心断层：

1. “选择视频结构”是 UI 心智，不是生产参数，结构没有进入真实脚本生成和视频任务。
2. “爆款模板”是卡片展示，不是表达蓝图，模板变量、论点 brief 和用户意图没有被完整采集。
3. 闪剪模板能力虽然已经有接口封装，但没有进入创建主流程，视频包装仍然依赖写死的 `styleId`。
4. 用户素材、BGM、证据画面没有成为镜头语言，只是零散资源，导致最终视频更像裸口播而不是营销视频。
5. 最终视频任务无法完整追溯导演层、编剧层和包装层的决策来源，后续无法复盘效果，也无法稳定调优。

从产品形态上看，`/create` 也被做成了一个“看起来有步骤”的向导页，但它还不是一个真正的创作工作台。它缺少三种中枢能力：

1. 不能稳定承接三层决策，只是在不同卡片间切换状态。
2. 不能可靠恢复和复用中间成果，用户一离开就容易重新开始。
3. 不能在高成本操作前给出清晰的总览和依赖校验。

## Goals / Non-Goals

**Goals:**

- 将视频创建正式定义为三层系统：导演层、编剧层、包装层
- 让结构蓝图真实驱动文案生成，而不是停留在前端状态
- 让闪剪模板成为正式包装层，并支持素材、BGM、字幕和布局能力的产品化表达
- 让最终视频任务可追溯结构、脚本模板、包装模板、素材和规则来源
- 在规范层为“更长、更完整、更有说服力”的营销脚本建立质量门槛，而不是接受一句话式候选稿

**Non-Goals:**

- 本 change 不直接实施前端或后端代码
- 本 change 不覆盖 `realman_broadcast`、`news_mixcut` 或纯素材新闻流的全量产品化，只先定义数字人主链路的包装体系
- 本 change 不重做运营后台或模板管理后台 UI
- 本 change 不引入新的计费模式、团队空间或多品牌工作区

## Product Quality Bar

- `/create` 必须像一个专业创作工作台，而不是会让用户反复走回头路的表单向导。
- 用户任何一次昂贵操作之前，都必须能清楚看到自己到底选了什么结构、什么文案、什么包装、什么数字人和声音。
- 上游决策一旦改变，系统必须诚实地让下游结果失效或待复核，而不是假装还能继续用。
- 文案、包装计划和最终视频任务都必须是可追踪的真实生产资产，不能只停留在浏览器本地状态。

## Decisions

### D1: 三层模型成为产品和架构的统一语言

**决定**:

- 导演层 = `VideoStructure`
- 编剧层 = `ContentTemplate + VideoCreativeBrief + IP Profile`
- 包装层 = `VideoPackagingTemplate + Material Assignments + BGM + Shanjian Rules`

任何创建页、prompt、任务或分析相关改动，都必须显式说明自己属于哪一层。

**为什么不是继续沿用“模板/步骤/素材”这种模糊说法**:

- “模板”这个词现在至少指代了三种不同对象，已经造成严重歧义。
- 如果不把三层对象彻底拆开，后续所有实现都会继续互相污染。

### D2: `/create` 是创作工作台，不是一次性步骤向导

**决定**:

`/create` 需要被设计成一个持续承接导演层、编剧层和包装层成果的工作台。它必须支持：

- 恢复未完成的创作状态
- 显示各层 readiness
- 在上游变化时明确让下游结果失效或待复核
- 在提交前展示完整 production summary

**为什么不是继续做一个轻量 wizard**:

- 视频生成是高成本、强依赖、可中断的工作流，不是一次性填写完表单就结束。
- 如果 `/create` 不能稳定承接中间结果，用户只会反复重做，系统也无法成为真正的创作中枢。

### D3: `/create` 维持 4 个可见阶段，但内部遵守 6 个子步骤

**决定**:

对用户仍然可以保留 4 个大阶段，以避免复杂度失控：

1. 定结构
2. 定表达
3. 定包装
4. 出视频

但系统内部必须遵守 6 个子步骤：

1. 选择视频结构
2. 选择内容模板
3. 填写本条视频 brief 并生成候选稿
4. 选择/编辑脚本
5. 选择闪剪包装模板并补素材/BGM
6. 选择数字人/声音并提交生成

**为什么不是把包装模板塞回最后一步**:

- 包装决定的不只是皮肤，而是素材策略、画面证据和镜头语言。
- 如果包装层放到提交前最后一秒，用户只能“选个皮肤”，拿不到真正的炫酷视频。

### D4: 新增结构对象与生产计划对象，而不是只在前端传几个参数

**决定**:

- 新增 `VideoStructure` 作为导演层实体，保存结构元数据与机器可用蓝图
- 新增 `VideoProductionPlan` 作为包装层实体，保存包装模板、素材分配、BGM 和包装规则
- 扩展 `ContentGenerationRun`，保存 `structureId` 与结构快照
- 扩展 `VideoTask`，保存 `productionPlanId` 与结构/包装快照

**替代方案**: 直接把 `structureId`、`styleId`、`materials[]` 塞进若干请求参数  
**不选原因**: 这会让关键生产决策继续停留在临时请求体里，无法复盘、复用和调试。

### D5: 文案生成升级为“四层输入 + 质量评分”的正式流水线

**决定**:

`POST /api/scripts/generate` 的规范输入升级为：

- `structureId`
- `templateId`
- `inputs`
- 可选 `hotTopic`

服务端必须组装四层输入：

1. IP 档案快照
2. 结构蓝图
3. 内容模板蓝图
4. 当前视频 brief

生成策略规范为：

- 先产出结构化大纲，再产出完整脚本候选
- 再由 evaluator 对候选稿做结构遵守、证据强度、CTA、口吻匹配和长度区间评分
- 不允许把明显不达标的一句话候选稿当作正常成功结果返回

**为什么不是继续 one-shot prompt**:

- one-shot 对“结构 + 模板 + 人设 + 观点 + 证据”这类多约束任务天然不稳。
- 我们要的是稳定可控的视频文案，不是偶尔抽中一次好结果。

### D6: 闪剪模板被定义为包装层能力，不是导演层或编剧层

**决定**:

- 闪剪模板来源于 `GET /v1/clip/template` 与 `GET /v1/clip/template/detail/{id}`
- Phase 1 以数字人主链路为主，优先使用 `scene=virtualman` 的包装模板
- “画中画”“证据插帧”“身份条”“标题栏”“重字幕风格”等能力，都作为模板能力标签展示，而不是全局 boolean 开关

**替代方案**: 给用户一个“开启画中画”或“开启炫酷包装”的总开关  
**不选原因**: 闪剪的实际能力取决于模板布局、素材位和规则组合，不存在稳定的万能开关。

### D6.1: 结构向下游输出“包装意图”，而不是直接支配闪剪模板

**决定**:

- `VideoStructure` 直接影响脚本生成，但不直接命令外部剪辑模板如何完成最终画面。
- 结构层需要向包装层输出一组可适配的 `PackagingIntent`，至少包括：
  - 节奏要求：快节奏 / 平稳递进 / 强转折
  - 证据密度：弱证据 / 中证据 / 强证据
  - 开场呈现：标题先出 / 人像直入 / 画面先行
  - CTA 强度：信任型 / 行动型 / 强转化型
  - 字幕策略：普通字幕 / 关键词高亮 / 强节奏断句
  - 素材需求：推荐素材角色、推荐数量、是否偏向 before-after / 资质 / 案例
  - BGM 倾向：轻氛围 / 节奏推动 / 情绪共鸣 / 无 BGM
- 包装层使用这组意图来：
  - 对闪剪模板做排序和推荐，而不是默认硬过滤
  - 预填 `packRules` / `processRules` 的默认值
  - 决定要向用户索取哪些素材角色与证据位
- 只有当模板能力与结构意图发生“技术上无法适配”的冲突时，系统才允许硬阻断某个模板。

**为什么不是让结构直接限制模板**:

- 外部模板池本来就少，结构如果变成硬过滤器，会让用户几乎没有选择。
- 最终可生产性掌握在闪剪模板能力上，不掌握在我们的结构定义上。
- 我们真正需要的是“按结构讲法去适配模板”，而不是假装外部模板会按我们的结构编排镜头。

### D7: 包装计划负责决定闪剪调用方式

**决定**:

对于数字人主链路：

- 简单包装计划默认映射到 `POST /v1/clip/video/virtualman_broadcast`
- 需要逐段素材分配、分镜级控制时映射到 `POST /v1/clip/video/custom_virtualman_broadcast`

包装计划还需要记录：

- `styleId`
- `materials[]`
- `backgroundMusic`
- `packRules`
- `processRules`
- 需要展示的模板能力标签

**为什么不是所有视频都走 custom 接口**:

- custom 更灵活，但也更复杂、更慢，维护成本更高。
- 主链路应该默认走更稳的标准接口，只有确实需要分场景控制时再升级。

### D8: 用户素材必须被定义为“证据角色”，而不是匿名文件列表

**决定**:

包装层采集用户素材时，需要为每个素材声明角色，例如：

- 产品细节
- 门店环境
- 操作过程
- 客户案例
- 资质证明
- Before/After

这些角色既用于 UI 引导，也用于后续脚本评分与视频生成策略。

**为什么不是只让用户随便传几张图**:

- 小白用户不会天然知道什么素材能撑住一条营销视频。
- 如果系统不主动引导素材角色，最终仍然会退化成“数字人念稿 + 几张随机图”。

## Risks / Trade-offs

- **包装层步骤变多，用户可能觉得麻烦** → 通过“推荐模板 + 推荐素材位 + 可跳过的高级项”降低门槛
- **闪剪模板目录会变化，直接在线使用不稳定** → 需要产品层做模板精选或缓存，不直接把原始接口结果裸露给用户
- **结构如果硬限制模板，会让本就稀缺的模板选择进一步收缩** → 结构下游默认只做“推荐排序 + 参数预设 + 素材要求”，仅在能力绝对不匹配时硬阻断
- **脚本质量门槛会带来更高生成成本和更长延迟** → 用候选评分阈值、重试上限和缓存策略控制成本
- **生产计划建模会增加后端复杂度** → 这是必要复杂度，换来的是可追踪性和后续稳定调优能力

## Migration Plan

1. 先将三层模型写入项目级规则与 OpenSpec，统一团队语言
2. 定义 `VideoStructure`、`VideoPackagingTemplate` / 模板缓存、`VideoProductionPlan` 的数据契约
3. 扩展 `/api/scripts/generate` 与 `/api/tasks` 契约，让结构层和包装层都能进入真实链路
4. 把 `/create` 重构成真正的三层创作工作台，补齐恢复、失效提示和最终总览
5. 再逐步把闪剪包装模板、素材匹配和 custom 接口的高级能力接入主链路

## Open Questions

- Phase 1 是否只开放少量精选包装模板，而不是把全部闪剪模板暴露给用户
- `VideoPackagingTemplate` 应该做本地持久化缓存，还是先做“服务端实时拉取 + 精选映射”
- 包装层是否允许“无素材直出”，还是要按模板能力强制若干关键素材位
- 文案质量门槛的默认长度区间是统一配置，还是按结构模板定义各自范围
- `PackagingIntent` 的正式字段集应收敛到哪一层：只作为服务端推荐输入，还是也要作为 `VideoProductionPlan` 的可追踪快照字段

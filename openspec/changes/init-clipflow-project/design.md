## Context

ClipFlow 是全新项目，从零搭建。核心价值链是：用户输入营销意图与文案 → 选择数字人和素材 → 系统生成带字幕和基础包装的营销视频 → 用户在视频库中预览、下载并复用成片。系统重度依赖闪剪 OpenAPI 的异步回调机制（数字人克隆 3-4 分钟，视频生成 30s-2 分钟）。

当前状态：空项目，仅有产品文档和 OpenSpec 配置。

约束条件：
- 目标用户是技术小白（中小企业主、电商卖家），UI 必须极简
- UI 组件库限定 shadcn/ui，不允许其他 UI 库
- 闪剪 API 为异步模式，必须通过 Webhook 接收结果
- MVP 范围：用户系统 + 资产管理 + 脚本系统 + 视频生成 + 视频库，不含自动发布
- MVP 必须保持“AI 视频生产平台”定位，不能只交付裸数字人口播能力

## Goals / Non-Goals

**Goals:**

- 搭建可运行的 Next.js 全栈项目，前后端统一在一个 repo
- 完整的用户认证流程（注册/登录/JWT）
- 数字人克隆全流程（上传 → 闪剪克隆 → Webhook 回调 → 状态就绪）
- 素材资产上传和复用流程（图片 / 视频 / 音乐）
- 视频生成全流程（选数字人 + 脚本 + 素材 → 闪剪生成 → Webhook 回调 → 视频可下载）
- 前端 3 步向导体验（输入文案 → 选数字人 → 生成视频）
- 首页和我的视频页提供最近视频、状态反馈和稳定下载入口
- 额度校验与成功后结算规则明确且可追踪
- Webhook 幂等处理 + 兜底轮询，确保不丢任务

**Non-Goals:**

- Chrome 插件半自动发布（MVP 后期）
- 外部账号绑定 OAuth（视频号/小红书，MVP 后期）
- 复杂视频模板系统
- 数据分析/报表
- 多语言 / 国际化
- 移动端适配（先做桌面端）

## Decisions

### D1: 全栈 Next.js（App Router）而非前后端分离

**选择**: Next.js App Router 统一前后端，API 路由放在 `app/api/` 下

**备选方案**:
- 前后端分离（Next.js + Express 独立部署）：增加部署复杂度，团队小没必要
- Python FastAPI 后端：产品文档提到可选，但前端已确定 Next.js，统一 TypeScript 生态更高效

**理由**: 单 repo 单部署，TypeScript 全栈类型共享，Vercel 一键部署，MVP 阶段开发效率最优。

### D2: Prisma ORM + PostgreSQL

**选择**: Prisma 作为 ORM，PostgreSQL 作为主数据库

**备选方案**:
- Drizzle ORM：更轻量但生态不如 Prisma 成熟，Prisma 的 migration 和 studio 工具更适合快速迭代
- 原生 SQL / pg 驱动：灵活但开发效率低，MVP 阶段不需要极致性能

**理由**: Prisma 类型安全、migration 管理成熟、与 Next.js 生态集成好。PostgreSQL 是产品文档指定方案。

### D3: NextAuth.js 认证

**选择**: NextAuth.js（Auth.js v5）处理认证，JWT 策略 + Credentials Provider

**备选方案**:
- 手写 JWT 认证：可控但重复造轮子，session 管理、CSRF 防护需要自己处理
- Clerk / Auth0：SaaS 认证服务，增加外部依赖和成本，MVP 阶段用户量小没必要

**理由**: NextAuth.js 是 Next.js 生态标准认证方案，JWT 策略无需 session 存储，后续易扩展 OAuth（视频号/小红书绑定）。

### D4: Redis 用途限定

**选择**: Redis 仅用于 Webhook 幂等去重（`webhook:{taskId}` key, TTL 24h）和兜底轮询锁

**备选方案**:
- Redis 作为全局缓存 + 队列：MVP 阶段用户量小（<1000），无需复杂缓存层
- 不用 Redis，数据库幂等：可行但 Webhook 高频场景下数据库压力大

**理由**: 最小化 Redis 使用范围，避免过度依赖。幂等去重是刚需，用 Redis SET NX + TTL 最简洁。

### D5: 阿里云 OSS 直传

**选择**: 前端通过后端获取 STS 临时凭证，直传 OSS；后端不做文件中转

**备选方案**:
- 后端代理上传：简单但后端成为瓶颈，大文件上传占用服务器带宽
- 预签名 URL 上传：与 STS 类似，但 STS 更灵活，支持细粒度权限控制

**理由**: 用户上传自拍视频和素材文件可能较大（几十 MB），直传 OSS 不经过服务器，减少带宽成本和延迟。

### D6: 前端轮询而非 WebSocket

**选择**: 前端每 5 秒轮询 `GET /api/tasks/:id` 查询异步任务状态

**备选方案**:
- WebSocket / SSE：实时性更好，但 MVP 阶段用户量小（<1000 并发），轮询足够
- 长轮询：实现复杂度高于简单轮询，收益不大

**理由**: 产品文档明确建议简单轮询方案。视频生成等待时间 30s-2min，5s 间隔体验可接受。后续可升级 SSE。

### D8: 闪剪 API 集成封装

**选择**: 统一封装 `lib/shanjian.ts`，暴露 `cloneAvatar()`, `generateVideo()`, `queryTask()` 三个方法

**理由**: 闪剪 API 调用涉及认证签名、参数组装、错误处理，统一封装避免散落各处。兜底轮询也复用 `queryTask()`。

### D9: 兜底轮询机制

**选择**: Next.js Cron（Vercel Cron Jobs）或定时 API 路由，每 5 分钟扫描超时任务

- 克隆任务：`status = cloning` 且 `updated_at` 超过 10 分钟
- 视频任务：`status = processing` 且 `updated_at` 超过 5 分钟

主动调用闪剪查询接口，按结果更新状态。

**理由**: Webhook 可能丢失（网络问题、服务端重启），兜底轮询确保任务不会永远卡住。

### D10: 资产模型以可复用素材为中心

**选择**: MVP 使用独立 `assets` 表管理用户上传的图片、视频和音乐素材；数字人克隆结果保存在 `avatars` 表；声音信息作为数字人的绑定属性进行展示，而不是单独开放声音克隆工作流。

**备选方案**:
- 仅实现数字人，不实现素材资产：会把产品收缩成“数字人工具”，偏离产品文档
- 单独建 `voices` 表并开放声音 CRUD：当前 PRD 没有独立声音创建流程，MVP 会引入额外复杂度

**理由**: PRD 明确要求资产中心覆盖数字人、声音和素材。MVP 用“数字人绑定声音信息 + 独立素材资产”即可覆盖核心需求，同时控制范围。

### D11: 视频输出契约是“可发布的营销成片”

**选择**: `video-generation` 能力的输出定义为带字幕和基础包装的营销短视频，而不是裸数字人口播片段。闪剪适配层负责屏蔽具体实现，允许通过上游参数或后处理流水线完成字幕和包装。

**备选方案**:
- 只生成数字人口播视频：实现更快，但偏离“AI 视频生产平台”的产品定位
- 一开始就做复杂模板系统：超出 MVP 范围

**理由**: 产品文档把字幕生成、视频包装写入核心产品价值。MVP 可以只做基础包装，但不能把这部分完全丢掉。

### D12: 额度采用“预检 + 成功结算”规则

**选择**: 创建任务前先基于脚本长度和默认语速估算生成时长，校验用户可用 credits 是否足够；任务成功后再根据最终视频时长按 `credits_cost = ceil(duration_seconds / 60 * 50)` 结算，不成功不扣费。

**备选方案**:
- 创建任务时立即扣费：会与 PRD “成功后扣费” 冲突
- 完全不做预检，等完成后再扣费：会导致余额不足用户也能占用生成资源

**理由**: 该方案同时满足 PRD 的成功结算要求和任务创建前的额度拦截要求，且能把 `credits_cost` 持久化到任务记录中。

### D13: 成片下载地址必须持久化到 OSS

**选择**: 视频生成成功后，后台在最终完成任务前将闪剪返回的视频拉取并保存到 OSS，再把 OSS URL 作为系统内的 canonical `video_url` 写入 `video_tasks`。

**备选方案**:
- 直接保存闪剪返回的临时 URL：实现最简单，但会让“我的视频”随时间失效
- 只在用户点击下载时临时转存：状态和重试逻辑复杂，且无法保证库内稳定性

**理由**: MVP 已包含首页最近视频和“我的视频”页，成片必须可稳定下载，否则视频库没有产品价值。

### D14: 发布系统在 MVP 中明确延后

**选择**: MVP 不实现 OAuth 账号绑定、`social_accounts` / `publish_sessions` 表、Chrome 插件或发布接口。生成完成页仅提供预览、下载和复制营销文案；如果保留“发布”入口，只能展示为 `Coming Soon`。

**备选方案**:
- 提前保留发布相关数据库和接口：容易产生范围膨胀和验收歧义
- 完全不提未来发布能力：会丢失 PRD 的后续方向

**理由**: PRD 已明确自动发布不在 MVP。把边界写清楚，既能防止范围漂移，也为后续变更留出独立空间。

## Risks / Trade-offs

- **闪剪 API 强依赖** → 闪剪服务不可用时整个视频生成链路中断。缓解：错误状态清晰展示，引导用户稍后重试；兜底轮询自动恢复。
- **Webhook 安全性** → 公开的 Webhook 端点可能被恶意调用。缓解：验证闪剪签名（如提供）；Redis 幂等去重防重放；仅处理已知 taskId。
- **OSS 直传安全** → STS 临时凭证泄露风险。缓解：凭证有效期控制在 15 分钟内，限制 bucket 和路径权限。
- **JWT 无状态** → 无法即时吊销 token。缓解：MVP 阶段可接受，后续可加 token 黑名单。
- **轮询性能** → 大量用户同时轮询可能造成 API 压力。缓解：MVP 用户量 <1000，5s 间隔可接受；后续可升级 SSE。
- **闪剪视频 URL 过期** → 闪剪返回的视频链接可能有有效期。缓解：在任务完成前转存至 OSS 并只对外暴露 OSS URL。
- **字幕/包装能力受第三方限制** → 如果闪剪能力不覆盖全部包装需求，裸口播视频会削弱产品价值。缓解：通过适配层保留后处理扩展点，并把“基础包装”定义成 MVP 验收标准。
- **额度估算与实际时长不完全一致** → 预检可能高估或低估成本。缓解：预检只用于准入，最终按完成时长结算并记录 `credits_cost`。

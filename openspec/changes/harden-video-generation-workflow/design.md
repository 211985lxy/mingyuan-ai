## Context

ClipFlow 当前的视频生成链路已经同时承载内容工作台和异步视频编排。当前系统的页面与流程已经持续演进，因此这次 hardening 不能假设要重做工作台体验，而应以“保留现有页面能力、收紧底层可靠性契约”为原则。问题不在于某一个接口会不会报错，而在于系统把多段高风险动作串成了一条缺乏统一状态边界的链路：

- 任务提交同时涉及余额校验、并发校验、闪剪异步任务创建、本地落库和计划消费
- 包装素材、BGM、训练素材、成片结果分别使用了不同层级的 URL 语义，没有统一的“上游可达”契约
- 任务终态既可能由 webhook 推进，也可能由 worker/cron 推进，还可能被详情接口推进
- 这使得当前系统虽然“能产出一个视频任务”，但离“可放心放量的生产中枢”还有明显差距。

本 change 的核心不是新增业务功能，而是把现有主链路的状态所有权、交付契约和用户提示统一起来。

## Goals / Non-Goals

**Goals:**

- 让视频任务提交具备一致的预占位、扣费、失败补偿和计划消费语义
- 让所有提供给闪剪读取的素材都经过统一的“上游可达”转换
- 让所有交付给用户的成片结果都具备显式的持久化状态，而不是静默使用临时链接
- 让任务终态推进收敛到统一的领域服务，避免多个 route handler 各自修改业务语义
- 让现有 `/create` 和视频详情页在不重写页面结构的前提下，继续只消费后端确认过的任务状态，不再由页面访问频率隐式推动上游状态

**Non-Goals:**

- 本 change 不扩展新的视频类型产品面，不把 `realman_broadcast`、`mixcut` 等能力一起产品化
- 本 change 不重做模板后台、运营后台或内容生成策略本身
- 本 change 不重做当前 `create`、`videos/[id]` 等页面结构与引导文案
- 本 change 不引入新的计费模型、套餐模型或组织协作模型
- 本 change 不要求一次性把所有媒资都改造成全新资产中心，只先收紧关键契约

## Decisions

### D1: 本地 `VideoTask` 成为唯一任务状态真相源，详情查询不再直接推进上游状态

**决定**

- `POST /api/tasks` 在调用闪剪前先在本地创建一个“已预占位”的任务记录
- `GET /api/tasks/[id]` 只读取本地状态、签名 URL、展示交付告警，不再直接调用闪剪 `getTaskInfo`
- 任务状态推进统一收敛到两个后台通道：
  - `POST /api/webhook/shanjian`
  - `runTaskRecoveryPass` 所在的 worker/cron

**为什么这样做**

- 当前详情接口既是查询接口，又是状态推进器，会让 UI 轮询频率直接影响上游负载和业务语义
- webhook 与 recovery 本来就是异步系统里更合理的推进者，详情接口应该只负责读“系统已知真相”

**替代方案**

- 保留详情接口主动查询闪剪，但加缓存或更长轮询间隔

**不选原因**

- 这样只是把问题减轻，没有把“状态所有权”收口
- 高峰期依旧会发生页面访问驱动上游状态的架构反模式

### D2: 任务提交改为“预占位事务 + 外部提交 + 显式补偿”的两阶段模型

**决定**

- 任务提交分为两个阶段：
  1. 本地事务阶段：锁定用户余额与并发占位，创建 `VideoTask(status=pending)`，必要时锁定 `VideoProductionPlan`
  2. 外部提交阶段：向闪剪提交任务；成功后将任务更新为 `processing + externalTaskId`，失败则统一走补偿流程
- `pending` 和 `processing` 一并计入活跃任务上限
- 失败补偿、计划释放、任务失败原因写入由统一补偿服务负责，而不是散落在各个 handler 里

**为什么这样做**

- 当前模型是“先查、后调、再扣、再落库”，任何一个中间环节出错都会导致一致性破裂
- 先创建本地任务，再走外部提交，至少能保证系统对所有高成本尝试都有账本记录

**替代方案**

- 继续使用“先调闪剪成功再扣费”的乐观模式，只补 transaction

**不选原因**

- 外部调用本身无法放进数据库事务，必须承认这是 Saga，并设计显式补偿
- 没有本地预占位就无法严肃处理并发、重试和孤儿任务

### D3: 所有给闪剪读取的输入资产都必须先经过 `resolveUpstreamReadableUrl` 统一转换

**决定**

- 引入统一的“上游可达 URL 解析层”，负责把以下输入转换成闪剪可读地址：
  - 数字人训练视频
  - 授权视频
  - 包装素材
  - BGM
  - 语音克隆源音频
- 对托管在私有 OSS 上的资源，统一生成临时签名 URL
- 对公共 HTTP URL，保留直传
- 对无法转换或不满足可达性的资源，在提交前显式失败，不再把错误留给闪剪隐式暴露

**为什么这样做**

- 当前系统只对部分资产做签名，包装素材和 BGM 没有进入同一个契约
- 产品提示里已经让用户填“OSS 地址”，后端就必须为此负责

**替代方案**

- 把生产计划里的 `fileUrl` 全部改成 `assetId`

**不选原因**

- 这是长期正确方向，但会扩大变更面
- 本次 hardening 先收口运行时契约，后续再演进成强资产引用模型

### D4: 结果交付必须显式区分 `durable` 与 `degraded`，不再把降级伪装成成功

**决定**

- 为视频交付增加显式交付状态，至少区分：
  - `pending`
  - `durable`
  - `degraded`
- `transferFromUrl` 改为真正的流式转存
- 转存失败时：
  - 任务业务状态仍可为 `completed`
  - 但交付状态必须写成 `degraded`
  - 必须记录告警文案和可选的失效时间
- `/api/tasks` 与 `/api/tasks/[id]` 必须返回显式交付元信息，供现有页面按需消费

**为什么这样做**

- 对用户而言，“能看 24 小时”和“能长期访问”是两个完全不同的结果
- 对产品而言，静默降级会把可靠性交给运气

**替代方案**

- 转存失败时直接把整个任务标为 `failed`

**不选原因**

- 有些场景下上游结果真实存在，业务上不应完全丢弃
- 但也不能伪装成完全成功，所以需要引入显式 degraded 语义

### D5: webhook、recovery、失败补偿和任务终态写入共用一套领域服务

**决定**

- 提取统一的任务终态处理服务，供以下入口复用：
  - webhook
  - task recovery
  - 任务提交补偿
- 统一服务负责：
  - 状态机校验
  - 补偿幂等
  - 结果转存
  - degraded 标记
  - 任务完成时间写入

**为什么这样做**

- 当前逻辑被拆在 `tasks/[id]`、`webhook/shanjian`、`task-recovery` 三处，行为正在分叉
- 同一个失败任务，不同入口可能得到不同结算结果，这是不能接受的

**替代方案**

- 保留各路由内部逻辑，只补几个共享 helper

**不选原因**

- helper 共享不了状态机语义和补偿顺序
- 需要的是一个真正的领域服务，而不是更多零散工具函数

## Risks / Trade-offs

- **[两阶段提交会让实现复杂度上升]** → 通过限制范围，只针对视频任务主链路先引入 reservation/compensation 模式
- **[把状态推进从详情接口移走后，部分场景的可见刷新速度会下降]** → 正常场景依赖 webhook，异常场景依赖 worker，必要时可加“手动刷新本地状态”而不是直接打上游
- **[统一终态服务会触及多个现有模块]** → 通过先抽领域层、再迁移入口，降低一次性重构风险

## Migration Plan

1. 先补 OpenSpec，冻结任务可靠性、媒资交付和用户提示的目标契约
2. 为 `VideoTask` 设计显式的活跃态与交付态，并补迁移脚本
3. 抽出统一的任务终态/补偿服务，让 webhook 与 recovery 先迁移到该服务
4. 重写任务提交路径，引入本地预占位事务和外部提交补偿
5. 引入上游可达 URL 解析层，并将包装素材、BGM 与已有训练素材接入同一契约
6. 将 `GET /api/tasks/[id]` 改成纯查询接口，并保证现有页面通过兼容的 API 字段读取可信状态

**Rollback**

- 如果两阶段提交上线后出现异常，可以临时保留旧提交路径作为 feature flag fallback
- 如果 degraded 状态短期内还没有页面消费，可以先保证 API 返回显式字段而不强制页面展示

## Open Questions

- `deliveryStatus` 是应作为 `VideoTask` 顶层字段，还是与交付元信息一起放到 `deliveryMetadata` JSON
- `pending` 任务的并发占位是否要区分“等待上游响应”和“已提交上游处理中”两种子态
- 包装素材是否在本次 change 就要求前端只能从资产库选择，而不是允许自由输入 URL
- 对于历史已经落库、但实际保存的是闪剪临时 URL 的任务，是否需要补一轮离线修复

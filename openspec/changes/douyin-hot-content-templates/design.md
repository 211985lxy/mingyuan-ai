## Context

ClipFlow MVP 已完成基础架构设计（Next.js App Router + Prisma + Redis + 闪剪集成），具备用户系统、数字人克隆、视频生成、脚本 AI 生成等核心能力。当前变更在 MVP 基础上增加三个维度：（1）抖音热榜数据采集，为用户提供营销选题灵感；（2）运营管理的内容模板库，让小白用户"选模板填信息"即可产出专业脚本；（3）为 1000 用户规模做并发管理和缓存优化。

当前状态：MVP 的 proposal/design/specs 已完成，代码正在实施中。

约束条件：
- 延续 MVP 的技术栈和架构决策（Next.js App Router、Prisma、Redis、Vercel 部署）
- 管理后台是内部工具，不面向终端用户，可简化 UI 投入
- 抖音热榜数据源为免费社区 API，无 SLA，必须有降级方案
- 模板系统需要人工运营介入，不能全自动化
- 1000 用户规模，无需引入消息队列或微服务

## Goals / Non-Goals

**Goals:**

- 每小时自动采集抖音热榜，前端可展示当前 Top 50 热搜话题
- AI 脚本生成可关联热点话题，至少 1 条脚本自然融入热点
- 运营人员可通过管理 API 创建、审核、发布带变量槽位的内容模板
- 用户可按行业和内容类型浏览模板，填入自身信息后渲染成完整脚本
- 模板可声明热点关联规则，系统根据当前热榜推荐匹配模板
- 用户级视频生成并发限制和每日配额控制
- 公共数据、热榜、模板列表的分层缓存策略

**Non-Goals:**

- 管理后台前端页面（本次仅做 API，管理端 UI 后续迭代）
- 模板自动生成（模板由人工策划，不是 AI 自动创建）
- 抖音视频内容抓取（只采集热搜关键词和热度，不抓取视频）
- 用户自建模板（模板仅运营团队管理）
- 实时推送热榜更新（用户侧通过缓存 API 读取，非 WebSocket）
- 精细化 A/B 测试或模板效果分析报表

## Decisions

### D1: 免费 API（xxapi.cn）+ 降级链，而非自建爬虫

**选择**: 使用 `https://v2.xxapi.cn/api/douyinhot` 作为主数据源，`https://api.vvhan.com/api/hotlist/douyinHot` 作为降级备用

**备选方案**:
- 自建爬虫直接抓取抖音内部 API（`douyin.com/aweme/v1/web/hot/search/list/`）：需绕过 `a_bogus` 反爬签名，法律风险高，维护成本高
- 付费 API（TikHub.io ~$0.001/次，TianAPI 付费套餐）：可靠性更高，但 1000 用户规模下每小时 1 次调用，免费方案完全足够
- 自建 DailyHotApi 实例：需要额外部署维护，本质仍是爬取抖音内部 API

**理由**: 每小时仅调用 1 次，免费 API 完全够用。降级链保证单一数据源不可用时自动切换。数据已经入库，即使两个源同时挂也有最近一批缓存可用。如果后续规模增长或需要更高 SLA，可无缝切换为付费 API（接口兼容）。

### D2: Redis 缓存 + DB 持久化双写，而非仅缓存

**选择**: 热榜数据同时写入 Redis（前端快速读取）和 MySQL（历史分析 + 降级兜底）

**备选方案**:
- 仅 Redis 缓存：实现最简单，但 Redis 重启后数据丢失，无法做历史趋势分析
- 仅 DB 持久化：查询走 DB 有延迟，频繁读取增加 DB 负担

**理由**: Redis 缓存 TTL 70 分钟（略长于 1 小时采集间隔，防间隙），前端读取走 Redis 零 DB 负担。DB 持久化保留 30 天历史，未来可做热点趋势分析和模板效果关联。

### D3: 模板变量用双花括号 `{{variable}}` 纯字符串替换，而非模板引擎

**选择**: 自建轻量 `{{variable}}` 替换引擎，不引入 Handlebars/Mustache/EJS 等模板库

**备选方案**:
- Handlebars/Mustache：功能强大（条件、循环），但模板系统面向运营人员，不需要编程逻辑，复杂语法反而增加出错概率
- EJS/Nunjucks：服务端模板引擎，功能过重，引入不必要的依赖和安全风险（模板注入）

**理由**: 营销脚本模板的需求是简单的"填空"——运营定义 `{{品牌名}}` `{{痛点}}` `{{卖点}}` 等槽位，用户填入信息后直接替换输出。纯 `String.replace` 实现仅 5 行代码，无依赖，无安全风险，运营人员一看就懂。

### D4: 管理员独立用户表 + 独立 JWT，而非复用用户系统加角色

**选择**: 新建 `AdminUser` 表和独立的管理员 JWT 认证，与普通用户完全隔离

**备选方案**:
- 在 `users` 表加 `role` 字段区分管理员：简单但混淆了两个完全不同的身份体系，管理员密码策略、登录审计、权限模型与普通用户差异大
- 使用第三方管理后台方案（Retool/AdminJS）：引入外部依赖，MVP 阶段模板管理功能简单，不值得

**理由**: 管理员是内部角色（运营人员），普通用户是外部客户，权限模型和生命周期完全不同。独立表 + 独立 JWT 确保安全隔离，管理端路由通过独立中间件校验 admin token，不会与用户认证逻辑交叉干扰。

### D5: 两级角色（editor/admin）而非多级 RBAC 权限系统

**选择**: 固定两级角色，editor 可创建和发布模板，admin 拥有全部权限含删除和用户管理

**备选方案**:
- 三级角色加审核流程（editor/reviewer/admin）：运营团队 <5 人，创建者和审核者往往是同一个人，审核流程是形式主义
- 完整 RBAC（角色-权限多对多表）：内部团队 <10 人，完全没必要
- 仅单一管理员角色：无法区分普通编辑和超级管理员（删除等危险操作）

**理由**: 运营团队初期 <5 人，审核流程是伪需求。editor 直接发布模板，admin 负责危险操作（删除、用户管理）。如果团队扩大到 10+ 人，再加 reviewer 角色和审核状态。

### D6: 模板生命周期为三状态（draft→published→archived），而非四状态加审核

**选择**: 三状态流转：draft（草稿）→ published（已发布）→ archived（已下架）

**备选方案**:
- 四状态加 review（审核中）：运营团队 <5 人，审核流程是额外负担，不如事后巡检
- active/inactive 两态：无法区分"从未发布"和"曾发布后下架"的模板

**理由**: 三状态足够覆盖模板的完整生命周期。draft→published（直接发布），published→archived（下架），archived→published（恢复）允许季节性模板循环使用。用户端仅看到 published 状态的模板，数据隔离清晰。后续团队扩大可加 review 状态。

### D7: 热点-模板关联基于关键词匹配 + 季节事件标记，而非 NLP 语义匹配

**选择**: 模板声明 `keywords`（关键词数组）和 `seasonalEvent`（季节事件标识），系统在当前热搜词中做简单包含匹配

**备选方案**:
- NLP 语义相似度匹配（embedding + 向量搜索）：效果更好但引入向量数据库依赖，1000 用户规模、几十个模板完全不需要
- 运营手动关联（每次热点出来手动绑定模板）：时效性差，运营负担重

**理由**: 模板数量 <100，热搜 50 条，简单的关键词 `includes` 匹配 + 季节事件日历足够覆盖需求。运营在创建模板时声明关键词即可，零运行时成本。后续如果模板库扩大到上千，再考虑 embedding 方案。

### D8: 用户并发限制基于 DB 计数，而非 Redis 令牌桶

**选择**: 提交视频任务前查询 `video_tasks WHERE user_id = ? AND status = 'processing'` 的 count，与套餐允许的并发数比较

**备选方案**:
- Redis 令牌桶/滑动窗口：经典限流方案，但 1000 用户峰值 25 并发，DB 查询完全可以承受
- 不做限制，依赖闪剪并发上限：闪剪并发超限直接报错，用户体验差

**理由**: DB count 查询足够快（有索引），代码最简单，且状态与实际任务完全一致。Redis 令牌桶在 DB 宕机时会与实际状态不同步，反而引入一致性问题。

### D9: Vercel Cron 执行热榜采集，而非外部调度器

**选择**: 使用 Vercel Cron Jobs（`vercel.json` 配置），触发 `GET /api/cron/douyin-hot`

**备选方案**:
- 外部调度器（cron-job.org / GitHub Actions 定时触发）：额外系统，增加维护和监控复杂度
- setInterval 常驻进程：Vercel Serverless 无法常驻

**理由**: MVP 已部署在 Vercel，Cron Jobs 是原生能力，零额外成本，配置简单。通过 `CRON_SECRET` 防止外部触发。

### D10: 管理后台仅 API（本次不做 UI），而非 AdminJS 或 Retool

**选择**: 本次仅实现管理端 REST API（挂载在 `/api/admin/*`），管理后台 UI 后续迭代

**备选方案**:
- AdminJS 自动生成管理界面：与 Next.js App Router 集成不佳，样式不可控
- Retool 低代码平台：SaaS 依赖，数据外流风险
- 同时做管理端前端页面：scope 膨胀，模板管理初期用 Postman/curl 或简易脚本足够

**理由**: 运营团队初期 <5 人，用 API 工具（Postman/Insomnia）或后续简单管理页即可操作。先把 API 和数据模型做对，UI 可以随时加。

### D11: 热榜数据保留 30 天，快照保留 90 天

**选择**: `DouyinHotItem` 保留 30 天后自动清理，`DouyinHotSnapshot` 保留 90 天

**备选方案**:
- 不做清理，全量保留：1000 用户规模下热榜数据月增 35MB，年增 420MB，不大但无限增长不优雅
- 仅保留最近一批：无法做任何历史分析

**理由**: 30 天热搜历史足够分析近期趋势和模板效果关联。每日 Cron 清理旧数据，保持 DB 整洁。快照记录保留更长（90 天）用于监控采集健康度。

## Risks / Trade-offs

- **免费 API 不可用** → 降级链自动切换（xxapi→vvhan→DB 最近缓存）。最坏情况下热榜停更数小时，不影响视频生成核心流程。如果频繁不可用，切换付费 API（TianAPI，月成本 <$10）。
- **热搜数据合规性** → 仅采集公开热搜关键词和热度值，不抓取视频内容或用户数据。数据用于灵感推荐，不做二次发布。风险较低。
- **模板质量依赖人工** → 模板由运营人员人工策划，初期模板数量可能有限。缓解：提供模板创建指南和 358 结构标准，降低创建门槛；首批准备 20-30 个覆盖核心行业的模板。
- **关键词匹配精度有限** → 简单 includes 匹配可能产生误匹配（如"苹果"同时匹配水果和科技）。缓解：运营可以设置更精确的关键词组合；1000 用户规模下误匹配影响有限，用户不满意可手动选择其他模板。
- **管理后台无 UI** → 初期运营通过 API 工具操作，效率较低。缓解：提供清晰的 API 文档和 Postman collection；管理端 UI 作为下一迭代优先事项。
- **并发限制可能影响付费用户体验** → free 用户限 1 并发可能感觉慢。缓解：限制是为了保护系统和闪剪并发配额，UI 上清晰说明"您有 1 个视频正在生成，完成后可提交下一个"，并提示升级。不设每日硬性配额，依赖 credits 体系自然限制总量，避免免费用户在探索阶段被硬性拦截导致流失。
- **Vercel Cron 精度** → Vercel Cron 最小粒度为 1 小时，且执行时间可能有数分钟偏差。缓解：热榜数据时效性要求不高（热搜变化频率远低于每小时），偏差可接受。

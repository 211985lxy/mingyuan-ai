## Context

ClipFlow 的 create 流程已经经历过几轮升级，现在的问题不是“有没有结构、模板、包装”这些页面元素，而是它们之间还没有形成一套足够稳定的产品和架构契约。

当前最突出的限制有 7 个：

1. 结构虽然已经进入真实脚本生成链路，但现有结构的用户表达仍然带较强行业心智，不利于跨行业复用。
2. “定表达”阶段当前仍按行业模板组织，这会把用户锁进行业心智，而不是表达逻辑。
3. 结构对下游包装层的影响目前主要停留在概念层，缺少正式的 `PackagingIntent` 契约。
4. 包装模板推荐没有被正式定义，结果是模板选择看起来像随机浏览，而不是系统在做专业引导。
5. Pexels 图片/视频已经接通，但它的边界没有明确写清：哪些素材角色可以 AI 补，哪些绝不能 AI 补。
6. BGM 没有真实上游 API，如果不把“手动模式优先”写进规范，系统很容易滑向假自动化。
7. create 主域实际上是 `virtualman`，但这层边界之前没有被明确写进规格，容易让非当前域模板混进流程。

这次设计需要解决的不是单一接口问题，而是把 create 工作台从“多模块串起来”升级成“一个有强产品语义的生产系统”。

## Goals / Non-Goals

**Goals:**

- 将结构库重写为 10 套无行业限制的通用结构，并沉淀为机器可用蓝图
- 将表达模板库重写为 10-20 套无行业限制的通用表达模板，并沉淀为机器可用蓝图
- 正式定义 `PackagingIntent`，让结构能继续影响模板推荐、参数预设和素材要求
- 明确 create 工作台当前只覆盖 `virtualman` 主域，避免伪支持其他视频类型
- 让 Pexels 图片/视频真实承担 AI 支持型素材补充，而不是停留在演示功能
- 明确 BGM 在当前阶段只能手动输入，不允许假装智能配乐已经成立
- 让模板推荐、失效规则、总结页和恢复语义都成为正式规范的一部分

**Non-Goals:**

- 本 change 不为 `realman_broadcast`、`broadcast_mixcut`、`news_mixcut` 提供新的 create UI
- 本 change 不引入自动 BGM 生成、自动 BGM 搜索或第三方 BGM API 集成
- 本 change 不替换 Shanjian 作为上游视频包装模板来源
- 本 change 不设计新的计费、团队协作或多项目空间能力

## Decisions

### D1: 结构库和表达模板库都必须去行业化，行业心智只留在 IP 层

**决定**:

- `VideoStructure` 只定义“怎么讲 / 怎么拍”，不再承载行业表达。
- `ContentTemplate` 也不再按行业组织，而是定义“用什么内容逻辑说服”。
- 行业归属只由 `IP` 档案承载。
- brief 只承载这一条视频的对象、卖点、证据、优惠和行动信息。
- 新结构库以通用拍摄/叙事手法为主，例如反差钩子、悬念递延、现场证明、对比翻转等。
- 新表达模板库以通用说服逻辑为主，例如痛点解决、教程步骤、清单推荐、见证、对比选择、幕后透明等。

**为什么不是继续把行业心智放在内容模板里**:

- 这样只是把问题从结构层挪到表达层，本质没变。
- 同一种见证、教程、对比逻辑本来就应该跨行业复用。
- 模板一旦按行业切分，brief 就会退化成填空题，模板库也会指数膨胀。

### D2: 表达模板需要升级为通用 expression blueprint

**决定**:

每个表达模板都必须输出可复用的机器字段，而不是只保留一段行业化口播稿。至少包括：

- `argumentPattern`
- `requiredBriefSlots`
- `optionalBriefSlots`
- `evidenceMode`
- `ctaStyle`
- `hotTopicModes`
- `recommendedStructures`

**为什么不是继续保留行业 starter templates**:

- 这类 starter templates 只能做示例，不能做稳定生产系统。
- 它们会让“定表达”阶段误导用户去选行业，而不是选表达逻辑。

### D3: 结构需要拆成脚本蓝图与包装意图

**决定**:

每个结构都必须输出两层机器语义：

- `StructureBlueprint`：服务于脚本生成，包括 opening pattern、narrative beats、pace、evidence density、cta style 等
- `PackagingIntent`：服务于包装适配，包括字幕强度、视觉优先级、模板能力偏好、推荐素材角色、BGM 倾向文案等

**为什么不是只保留一个 blueprint**:

- 只保留脚本蓝图会让结构在包装层失效，用户感知不到结构的下游价值。
- 直接让结构命令模板如何剪又是不现实的，因为真正的渲染能力掌握在外部模板上。

### D4: 模板推荐以排序和预设为主，而不是硬过滤

**决定**:

- 结构 + 脚本 + 模板能力共同生成模板适配分。
- 系统默认把模板分成 `recommended`、`acceptable`、`weak-fit` 三档。
- 只有当模板缺失当前结构/脚本所必须的能力时，才允许硬阻断。

**为什么不是让结构直接限制模板列表**:

- 当前 Shanjian 模板池不够宽，硬过滤会迅速把用户选择压缩到几乎不可用。
- create 工作台需要“专业推荐感”，不是“系统替你删光选项”。

### D5: 当前阶段的 AI 包装辅助以 Pexels 支持型素材为主

**决定**:

- AI 自动补素材只使用 Pexels 图片/视频作为支持型素材来源。
- AI 只允许补 `product_detail`、`store_environment`、`process` 这类支持角色。
- `customer_case`、`qualification`、`before_after` 必须保留为手动真实素材。

**为什么不是让 AI 补所有角色**:

- 真实性风险太高，容易让用户误把通用图库素材当成真实案例或资质。
- 这会直接破坏营销可信度，也违背当前产品的真实生产定位。

### D6: BGM 在当前阶段必须明确为手动能力

**决定**:

- create 工作台允许用户上传或选择受管 BGM 资产。
- 系统可以输出 BGM 风格建议文案，但不能自动落参、自动选曲或伪造自动 BGM 成功状态。

**为什么不是先做一个“智能 BGM”占位能力**:

- 没有真实接口支撑的自动能力会违反零 mock 铁律。
- 一旦产品文案暗示自动能力存在，后续实现和用户预期都会被拖偏。

### D7: `/create` 维持 4 个可见阶段，但内部要有更细的推荐与失效语义

**决定**:

可见阶段维持：

1. 定结构
2. 定表达
3. 定包装
4. 出视频

但内部必须明确这些隐式子步骤：

1. 选结构
2. 选表达模板
3. 填 brief 生成候选稿
4. 选中脚本
5. 看包装推荐并选模板
6. 补素材/BGM
7. 选数字人并提交

同时定义失效规则：

- 改结构：脚本、推荐模板、AI 素材建议全部失效或待复核
- 改脚本：包装推荐和 AI 素材建议待复核
- 改模板：参数预设和 AI 素材建议待复核
- 手动素材尽量保留，AI 素材默认重算

**为什么不是继续把一切都塞在阶段 3/4**:

- 这会让工作台看起来像表单页，而不是专业工作流。
- 推荐、失效和总结都需要有自己的正式语义，不能只靠临时 toast。

### D8: 当前 create 主域明确收敛到 virtualman

**决定**:

- 当前 create 工作台只面向 `virtualman_broadcast` / `virtualman_video` 兼容的内容模板和包装模板。
- 非当前域模板必须在选择前就被隐藏或明确标注不可用，不能等到最后提交时报错。

**为什么不是继续“显示但不支持”**:

- 这会制造强烈的坏 UX，用户会觉得系统在引导他走向错误路径。
- 既然产品域已经明确，就必须在工作台入口层就诚实收口。

### D9: 生产计划需要保存足够的推荐上下文和血缘

**决定**:

- `VideoProductionPlan` 继续保存结构、模板、素材、BGM、pack/process rules。
- 同时要允许保存推荐来源或推荐快照，例如结构意图、推荐等级、推荐理由摘要，以支持之后的复盘。

**为什么不是只保留最终选择结果**:

- 只保留结果会让后续无法判断“为什么当时推荐这个模板”。
- create 工作台后续需要持续优化模板推荐，必须有可追踪数据。

## Risks / Trade-offs

- **[结构和表达模板都更抽象，用户可能一开始不理解]** → 用一句话解释、适用目标、证据要求和示例语言降低理解成本
- **[模板池少，推荐排序可能看起来变化不大]** → 优先把推荐理由和参数预设做好，让推荐仍然有感知价值
- **[Pexels 素材质量不稳定]** → 仅用于支持型素材角色，并要求 durable 转存完成后才能进入生产计划
- **[BGM 手动模式会降低“智能感”]** → 用诚实能力边界换取可信度，先保留风格建议文案而不是伪自动
- **[只支持 virtualman 可能限制短期覆盖面]** → 明确这是一阶段域边界，避免错误承诺，后续再为其他域设计独立旅程

## Migration Plan

1. 先完成 OpenSpec：结构系统、模板推荐、包装链路、工作台和主旅程改写
2. 定义新的结构 seed 数据和机器字段，并迁移或下线旧的行业化结构
3. 定义新的表达模板 seed 数据和机器字段，并迁移或下线旧的行业化内容模板
4. 统一包装模板能力标签，补齐推荐服务和参数预设规则
5. 更新 `/create` 前后端契约，让推荐、失效、Pexels 素材建议和 manual-only BGM 进入真实链路
6. 通过集成测试和真实数据库验证后，再考虑把 change 同步到 main specs

## Open Questions

- `PackagingIntent` 应该完整持久化到 `VideoProductionPlan`，还是只保存推荐摘要
- 表达模板是否需要独立 capability/spec，还是继续挂在 content generation 能力下
- 模板推荐结果是否需要单独接口，还是直接并入模板列表/详情接口
- 10 套结构与 10-20 套表达模板是否一次性全上线，还是先挑首发集合
- 是否需要在脚本选择后，对脚本做一次 lightweight parsing 来增强模板推荐和 Pexels 查询词
